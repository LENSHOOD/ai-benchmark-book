# 实践环境

本书提供两套可以在本机直接运行的参考实现，不需要 API Key：

| 项目 | 主要环境 | 关键风险 | 入口 |
|---|---|---|---|
| 云舟零售履约异常 | 订单、库存、物流、退款和审批 | 越权拆单、错退款、重复动作、未升级 | `examples/commerce_supply_chain/` |
| 星桥硬件研发门禁 | 需求、BOM、测试、缺陷和工程变更 | 无证据放行、危险替代料、漏掉安全缺陷 | `examples/hardware_rnd/` |

在仓库根目录运行：

```bash
python3 -m unittest discover -s examples -p 'test_*.py' -v
python3 examples/run_all.py
```

默认“模型”是一套结果可复现的规则策略，公开输入不含评分器的目标状态和答案。程序会用固定随机种子注入四类故障：调用前失败、只写入一部分、写入成功但响应丢失、服务不可用。Workflow 版本先查询状态，再决定补全未提交部分、确认成功或重试。

这些成绩只用于教学。它只能证明运行器、任务、环境和评分器能识别预先设计的错误。换成真实模型后，还要记录服务商、模型快照、推理设置、预算、重试和完整输出。

## 贯穿练习

每章练习都会留下一个可以继续用的文件。依次完成后，你会得到评测章程、能力定义图、任务清单、任务规范、评分器说明、Harness 说明、实验计划、发布门禁和复证计划。

## Lab 1：检查公开接口不含答案（15 分钟）

**目标**：检查被测系统（SUT）的公开输入边界。运行全套测试，再打开 `examples/test_benchmark_core.py`。测试检查 `PublicTask` 不携带目标答案，以及把私有 `target_state` 改成不可能值后，原输出会被判失败。后一项证明评分器使用了私有答案，不能单独证明策略没有其他读答案的途径。

```bash
python3 -m unittest examples.test_benchmark_core -v
```

**预期产物**：列出 `PublicTask` 的可见字段、`Task` 的私有字段，以及自己的系统怎样隔离答案。还要检查一个 trial 修改公开视图后，是否会污染私有任务或下一次运行。同进程的类型分离不是安全沙箱；接入能读文件或执行 shell 的 Agent 时，必须隔离答案文件与评分进程。

## Lab 2：检查状态、veto 与替代路径（30 分钟）

**目标**：确认评分器不奖励“说得漂亮”，也不要求系统只能走一条固定路径。选择 `cs-004` 或 `hw-003`，构造三种输出：换一条路径但结果正确、看起来接近但结果错误、通过危险捷径完成。运行 `grade()`，预期依次得到 pass、fail、veto。

**自检**：正确的替代路径不会因为 action 名称不同而被拒绝；危险动作即使其他分数很高，仍然是零分；缺少目标状态时，不能靠一段“证据说明”补过关。

再加入两个自然组成的错误：同一订单用两个不同请求键退款；审批待处理却发送“已退款”的结构化通知。不要只测试预先命名的坏动作。这里构造输出是为了攻击评分器；正式运行的状态与证据必须由可信环境收集，不能由模型填写。

## Lab 3：观察四类工具故障（半天）

**目标**：理解为什么多跑几次必须真的改变执行条件。`StatefulEnvironment` 会根据随机种子选择调用前失败、部分写入、响应丢失、服务不可用或无故障。对同一候选和任务打印完整记录，比较 Direct 与 Workflow。Direct 可能留下“不知道写没写成功”的状态；Workflow 会先查询幂等状态，再决定是否重试。服务一直不可用时，结果必须标成证据不足。

**预期产物**：一张“故障类型—正确处理方式”表、两条代表性运行记录，以及一个新增恢复测试。重点比较故障发生瞬间的状态：部分写入只能完成一部分，响应丢失则已完整提交。恢复之后都要检查是否重复产生副作用，不能只看日志名称。环境不可用应保留为证据不足。

成本与延迟也是测试对象。失败尝试、成功执行、去重确认和恢复查询都应按公开规则记账。当前数值是合成成本和时长，不是实测账单或墙钟时间；没有任何成功案例时，单位成功成本应标成无法计算。

## Lab 4：任务级配对而非伪重复（30 分钟）

运行两个 suite，检查 `paired_tasks`、`total_trials` 与 `ci95`：

```bash
python3 examples/commerce_supply_chain/run.py
python3 examples/hardware_rnd/run.py
```

每套有 10 个任务，每个候选在每道题上运行 4 次。比较函数应该报告 10 个配对任务，以及两个候选合计 80 次运行。它不能把 40 次重复运行说成 40 个独立配对样本。把运行次数改成 2 后，`paired_tasks` 仍应是 10。

## Lab 5：生成可复现运行包（15 分钟）

```bash
python3 examples/run_all.py
```

命令会在 `examples/results/` 下创建两个新目录，不会覆盖旧结果。检查 `run_manifest.json` 是否记录题集和评分器版本、任务数、候选数、随机种子数，以及出现结果差异的单元数。再检查每次运行是否记录身份、随机种子、环境哈希、失败类型、成本、延迟、轨迹和证据不足。第二次运行不能覆盖第一次结果，重复导入同一 trial 也不能悄悄增加权重。

## Lab 6：把一个业务流程移植进来（一周工作坊）

使用[模板指南](/appendix/templates)完成评测章程、任务规范、评分器说明和发布门禁。至少选择一个真实顺利案例、一个经过多次交接的案例，以及一个事故或险情。基于它们生成正常、近错、缺少证据和工具故障四类题。

请另一位同事在不询问出题人的情况下重跑。凡是必须靠作者口头解释的字段或判断，都要进入问题清单并改进文档。

先按[双案例工件走读](/labs/worked-artifacts)填完同一任务的章程、规范、评分器与门禁，再读[模型动作接口](/labs/model-adapter)。接入顺序是公开任务与工具说明 → 模型提出动作 → 可信环境执行 → 独立评分。模型不能自报最终状态、证据或自己是否通过。

真实模型服务异常、预算耗尽、业务动作失败要分别记。先用无网络的假模型检查接口和错误处理，再接选定服务商；本书没有调用付费模型或真实企业系统。
