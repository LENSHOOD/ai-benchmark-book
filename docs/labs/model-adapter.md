# 怎样把规则策略换成模型

先运行这个不需要 API Key 的示例：

```bash
python3 -m examples.action_adapter
python3 -m unittest examples.test_business_receipts -v
```

演示使用 `cs-004` 高额退款审批任务和固定故障 seed。假模型提出动作，环境实际更新模拟状态，再由独立 grader 检查。输出里的 `passed` 应为 `true`，轨迹中可以找到 `partial_write`、`query_idempotency` 和 `resumed`。

这里故意保留三个角色：模型只建议做什么，环境记录实际做了什么，评分器判断结果是否符合私有任务要求。把角色分开，比先选某个服务商 SDK 更重要。

## 唯一需要替换的函数

打开 `examples/action_adapter.py`。`run_actions()` 接受一个 `choose(context)` 函数。演示用预先写好的动作序列实现它；接入真实模型时，在这个函数里调用所选服务商，再把响应解析成一个动作请求。

模型可见的上下文包括公开任务、允许的工具名称、当前状态和操作轨迹。`target_state`、`required_evidence` 等私有答案不进入模型输入。真实工具还需要参数 schema；这个教学接口只演示固定动作和请求键。

一个正常请求长这样：

```json
{"action": "create_refund_approval", "key": "approval-1", "recover": false}
```

工具未确认完成时，模型可以对同一个动作、同一个键发出 `recover: true`。控制器会先查请求状态；完整提交只需确认，部分提交继续未完成的步骤。返回 `None` 表示停止，但是否成功仍由 grader 决定。

不要让模型返回 `final_state` 或 `passed` 再原样交给评分器。本示例会拒绝这些额外字段，状态、通知回执和证据均由环境产生。给模型的字典是副本，它修改自己的观察不会改掉宿主状态。

## 失败怎样记

| 情况 | 本地处理 | 正式接入还要记录 |
|---|---|---|
| 模型调用抛异常 | `provider_error`，证据不足 | 服务请求 ID、错误类别、已经产生的费用 |
| 响应不符合动作格式 | `invalid_action_request`，证据不足 | 原始响应、解析器版本、重试规则 |
| 操作次数达到上限 | `step_budget_exhausted`，证据不足 | token、墙钟和金额预算，各自的停止条件 |
| 环境持续不可用 | 保留 `environment_error`，不删行 | 服务故障与模型错误分开统计 |
| 模型自己说完成 | 环境停止，评分器仍查终态 | 不能靠自报成功跳过验收 |

当前只限制循环次数，没有硬中断一个迟迟不返回的模型调用。真实 provider wrapper 必须设置请求超时，并记录包括失败调用在内的真实 token 和成本。本地的 `cost_units`、`latency_ms` 是合成工具计量，不包括模型费用。

## 接入之前的四个动作

先把公开上下文序列化为输入，再严格解析模型响应；只调用允许的工具；保留完整运行记录；最后在模型看不到的评分端验收。用现有测试确认它拒绝自报状态、正确处理异常和预算耗尽，再使用一个很小的开发集接入模型。

本例在同一个 Python 进程里执行可信代码，不能隔离恶意插件。真实 shell Agent 应运行在单独进程或容器里，隐藏答案文件，限制网络、文件与工具权限。示例没有连接真实订单、支付或硬件系统。
