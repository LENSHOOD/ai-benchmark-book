# Eval、Benchmark 与排行榜

> **本章问题**：团队说“做个 eval”时，究竟可能在说哪几件不同的事？

术语混乱不只是说法不同，它会直接让团队做错事。有人把十条 Prompt 回归测试叫 benchmark，有人把公开排行榜叫 eval，也有人把生产监控叫 benchmark。如果不先说清楚，团队很容易拿研发测试回答采购问题，拿用户满意度判断业务是否正确，甚至拿模型榜单决定数字员工能不能上岗。

## 四个容易混淆的对象

**Evaluation（评估）**是一个大类。只要是在有意收集证据、判断系统表现，都算 evaluation。它可以在线或离线、正式或探索、自动或人工完成。

**Eval（一次具体评测）**通常指一项可以实际运行的评测，包括任务、数据、运行规则、grader 和结果。产品团队也常把一组回归测试称为 eval suite（评测套件）。

**Benchmark（基准评测）**更强调标准化和可比较。它通常有相对稳定的任务范围、公开的运行规则、明确版本和指标，让人可以比较不同系统，或者比较同一系统在不同时间的表现。

**Leaderboard（排行榜）**只是展示结果的一层。它挑出一些分数进行排序，但不一定会展示不确定性、成本、未完成的运行、版本变化，或不同结果之间其实不可直接比较的条件。

还要区分两种 harness。**Agent harness（Agent 运行框架）**是被测系统里的控制层和工具层，它决定 Agent 怎样工作。**Evaluation harness（评测运行框架）**负责加载任务、调用系统、收集操作记录、评分和汇总，它决定我们怎样观察系统。两者都会影响结果，但不能混为一谈。

## 八层测量系统

::: warning 实践建议 · 本书框架
“八层测量系统”是本书用于检查证据链完整性的工作框架，不是外部标准或成熟度认证。它在全书中的位置以及与其他框架的关系见[框架总览](/appendix/framework-map)。
:::

本书用下面八层来拆解一个 benchmark：

| 层 | 要回答的问题 | 常见错误 |
|---|---|---|
| 构念 | 想测什么，明确排除什么 | 用宏大名称掩盖具体任务需求 |
| 任务宇宙 | 部署中有哪些正常、边界与危险情形 | 只收集 happy path |
| 项目 | 有限题目如何从宇宙抽样 | 随机行切分导致实体泄漏 |
| 协议 | 输入、工具、预算、重试和停止是什么 | 看到结果后调整条件 |
| 环境与被测系统 | 哪个版本组合被测，环境如何重置 | 只写模型名 |
| Grader | 什么证据算完成，什么是 veto | 用文本相似度替代状态正确 |
| 统计与解释 | 分数多稳定，能外推到哪里 | 只报总均值和小数点 |
| 生命周期 | 如何修订、监测、申诉和退役 | 把题集当永久真理 |

这八层不是八份互不相关的表格，而是一条证据链。先定义想测的能力，再决定任务要覆盖什么；任务又决定环境要模拟什么；环境决定 grader 能看见什么；统计分析决定这批结果能支持多重要的决策；生命周期管理则决定证据什么时候过期。

## 一次运行不是能力值

把某次运行记为：

```text
Observation = f(system version, task instance, environment state,
                protocol, randomness, grader, infrastructure)
```

能力不是这一次运行本身，而是我们根据多次观察推测出来的属性。一次通过，可能靠的是猜测、答案泄漏、工具偶然成功，或者 grader 太宽松；一次失败，也可能只是环境出了故障。所以报告至少要保存每道任务的结果、系统配置、随机种子、操作轨迹、环境错误和 grader 版本。

“模型 A 得了 73.2 分”这句话缺了很多关键信息。更完整的说法应该是：“模型 A 的某个快照，配合 Harness H2、Skill S4 和工具集合 T，每题最多花 2 美元、运行 10 分钟，在 suite v1.3 的隐藏集上跑 3 次，再由 grader g5 评分，严格成功率是……”这句话确实长，但想让两个结果真正可比，这些信息不能省。

## 诊断、资格与生产证据

可以用三层结构避免用途错配：

**诊断层**回答系统哪里强、哪里弱。题目可以对研发开放，也可以给部分分，重点是快速迭代并标出具体失败原因。

**资格层**回答系统是否可以发布或获得某项权限。它需要隐藏任务、提前固定运行规则、严格的成功标准、安全否决项，以及明确的失败处理方式。

**生产层**回答上线后的表现能否持续。它要观察任务分布、人工接管、成本、多个任务同时失败和新型事故，并把重要失败转成回归任务。

一个题集可以在不同阶段承担不同角色，但不能同时对研发完全可见又声称是无偏资格集。

## 用“决策—证据”矩阵结束术语争论

团队争论某个东西是否算 benchmark，往往不如直接问它支持哪项决策。

| 决策 | 最低证据 | 不能只靠什么 |
|---|---|---|
| 修复 Prompt 回归 | 稳定开发集、逐题差异、失败分类 | 公共排行榜 |
| 选择基础模型 | 共同任务、固定运行框架、预算匹配 | 厂商各自发布表 |
| 采购 Agent 产品 | 完整产品测试、成本、风险和操作记录 | 只写模型名的成绩 |
| 发布新 Skill | 无 Skill 对照、组件消融、过期/冲突与关键退步 | 平均提升 |
| 数字员工上岗 | 私有资格、风险集、基线、门禁和影子证据 | 通用能力总分 |
| 扩大权限 | 生产复证、事故回归、可恢复性和责任人 | 单次资格通过 |

规律很简单：一个决定越难撤销，出错损失越大，所需证据就越要接近真实部署，也越要防止泄题并覆盖少见但严重的风险。反过来，在早期探索阶段，评测应该便宜、快速、能指出问题，不需要每次改 Prompt 都请专家做昂贵评审。

## 每次运行的结果都要单独保存

很多团队只保存一张汇总 CSV，后来想换一种统计方法，却发现原始信息已经丢了。更稳妥的做法是把每次试验（trial）都单独保存。记录里至少要有：评测套件、任务和版本；完整系统组件；初始环境快照；输出与操作记录位置；grader 和断言版本；严格成功、诊断分和 veto；成本与延迟；环境错误；人工仲裁结果和时间。

```json
{
  "task_id": "cs-004",
  "candidate": "model@2026-08+harness@3+skill@7",
  "trial": 2,
  "strict_success": false,
  "veto": "refund_without_approval",
  "environment_error": null,
  "grader_version": "refund-grader@5"
}
```

原始记录不要覆盖，汇总表随时可以重算。grader 修改后，要保留旧分数并生成一版新分数。只有这样，团队才能解释榜单变化到底来自系统，还是来自评分方法。

## “未评估”不是零分

环境失败、因为预算没跑、工具不兼容和候选拒绝提交，是四种不同情况。全部记成零分，会把基础设施问题算到系统头上；全部删掉，又会让结果看起来过于漂亮。报告要保留 `not_run`、`environment_error`、`invalid_output`、`graded_failure` 等状态，并公开每类有多少。哪些情况进入主要分母，必须在运行前写进规则，不能看到结果后再决定。

## 双案例镜头

云舟零售的诊断集可以给“选对仓库但通知错误”部分分；资格集必须要求库存预留、订单状态、客户通知和禁止动作全部正确。星桥硬件的诊断集可以评价根因分析质量；DVT 放行资格必须要求安全测试证据、需求追踪和审批状态同时成立。

## 实践检查单

- 文档中每次出现“模型成绩”能否替换成完整系统配置？
- 研发可见题和资格隐藏题是否分开？
- 环境故障是否有独立状态，而非从分母删除？
- Leaderboard 是否把不同预算或工具条件放在同一列？
- 每个指标最终改变哪项决策？

## 练习：拆解一张排行榜

任选一张公开排行榜，补全它省略的八层信息。对无法找到的信息标记“未披露”，不要推测。最后写出三个该榜单能支持的结论和三个不能支持的结论。
