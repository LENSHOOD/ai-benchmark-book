# Eval、Benchmark 与排行榜

> **本章问题**：团队说“做个 eval”时，究竟可能在说哪几件不同的事？

术语混乱不是文字问题，而会直接改变工程范围。有人把十条 Prompt 回归叫 benchmark，有人把公开排行榜叫 eval，有人把生产监控也叫 benchmark。若不先消歧，团队会用研发测试回答采购问题，用用户满意度回答正确性问题，用模型榜单回答数字员工上岗问题。

## 四个容易混淆的对象

**Evaluation（评估）**是一切有意收集证据、判断系统表现的活动。它可以离线或在线、正式或探索、自动或人工。

**Eval** 常指一项具体评测：任务、数据、运行协议、grader 和结果。产品团队也常把回归测试集合称为 eval suite。

**Benchmark** 强调标准化与比较。它通常有相对稳定的任务总体、公开协议、版本和指标，允许跨系统或跨时间比较。

**Leaderboard** 是展示层。它选择某些分数排序，却可能不展示不确定性、成本、缺失运行、版本变化或不可比较条件。

此外还要区分两个 harness：**agent harness** 是被测系统的控制与工具层；**evaluation harness** 是装载任务、调用系统、收集轨迹、评分和汇总的测量基础设施。前者决定 Agent 如何工作，后者决定我们如何观察。两者都能影响结果，但角色不同。

## 八层测量系统

::: warning 实践建议 · 本书框架
“八层测量系统”是本书用于检查证据链完整性的工作框架，不是外部标准或成熟度认证。它在全书中的位置以及与其他框架的关系见[框架总览](/appendix/framework-map)。
:::

本书采用八层语言描述任何 benchmark：

| 层 | 要回答的问题 | 常见错误 |
|---|---|---|
| 构念 | 想测什么，明确排除什么 | 用宏大名称掩盖具体任务需求 |
| 任务宇宙 | 部署中有哪些正常、边界与危险情形 | 只收集 happy path |
| 项目 | 有限题目如何从宇宙抽样 | 随机行切分导致实体泄漏 |
| 协议 | 输入、工具、预算、重试和停止是什么 | 看到结果后调整条件 |
| 环境与被测系统 | 哪个版本组合被测，环境如何重置 | 只写模型名 |
| Grader | 什么证据算完成，什么是 veto | 用文本相似度替代状态正确 |
| 统计与解释 | 分数多稳定，能外推到哪里 | 只报总均值和小数点 |
| 生命周期 | 如何修订、监测、申诉和退役 | 把题集当永久真理 |

这八层不是流程图上的八个表格，而是证据链。构念决定任务需要覆盖什么；任务决定环境要模拟什么；环境决定 grader 能观察什么；统计决定结果能支持多强的决策；治理决定证据何时过期。

## 一次运行不是能力值

把某次运行记为：

```text
Observation = f(system version, task instance, environment state,
                protocol, randomness, grader, infrastructure)
```

能力是我们根据观测推断的潜在属性。一次通过可能来自猜测、泄漏、工具偶然成功或宽松 grader；一次失败也可能来自环境故障。因而报告应至少保存任务级结果、配置、种子、轨迹、环境错误和 grader 版本。

“模型 A 得 73.2”是一个不完整句子。完整表达应类似：“模型 A 的某快照，在 Harness H2、Skill S4、工具集合 T、每题 2 美元和 10 分钟预算下，于 suite v1.3 的隐藏集运行 3 次，经 grader g5 评分，严格成功率为……”。这看起来啰嗦，却是可比较性的最低成本。

## 诊断、资格与生产证据

可以用三层结构避免用途错配：

**诊断层**回答哪里强、哪里弱。它允许部分分、可见题、快速迭代和细粒度失败标签。

**资格层**回答是否发布或授权。它需要隐藏任务、预注册协议、严格成功、安全 veto 和明确的失败处理。

**生产层**回答真实部署是否持续成立。它观察分布、接管、成本、共同故障和新型事故，并将失败转回回归。

一个题集可以在不同阶段承担不同角色，但不能同时对研发完全可见又声称是无偏资格集。

## 用“决策—证据”矩阵结束术语争论

团队争论某个东西是否算 benchmark，往往不如直接问它支持哪项决策。

| 决策 | 最低证据 | 不能只靠什么 |
|---|---|---|
| 修复 Prompt 回归 | 稳定开发集、逐题差异、失败分类 | 公共排行榜 |
| 选择基础模型 | 共同任务、locked harness、预算匹配 | 厂商各自发布表 |
| 采购 Agent 产品 | Native-product 赛道、成本、风险和 trace | 只写模型名的成绩 |
| 发布新 Skill | 无 Skill 对照、消融、过期/冲突与关键负增益 | 平均 lift |
| 数字员工上岗 | 私有资格、风险集、基线、门禁和影子证据 | 通用能力总分 |
| 扩大权限 | 生产复证、事故回归、可恢复性和责任人 | 单次资格通过 |

矩阵揭示了一条规律：决策不可逆、损失越大，证据越需要接近部署、保持隐藏并包含尾部风险。反过来，探索阶段应允许便宜、快速和有诊断力，不必把每次 Prompt 修改都送入昂贵专家评审。

## Evaluation Result 应是一等数据对象

很多团队把 eval 输出做成 CSV 总表，导致后续无法重新聚合。更稳妥的逐 trial 记录至少包括：suite/task/version；完整系统组件；初始环境快照；输出与 trace 指针；grader/断言版本；strict/diagnostic/veto；成本与延迟；环境错误；人工仲裁和时间。

```json
{
  "task_id": "cs-004",
  "candidate": "model@2026-08+harness@3+skill@7",
  "trial": 2,
  "strict_success": false,
  "veto": "refund_without_approval",
  "environment_error": null,
  "grader_version": "refund-grader@5"
}
```

原始记录不可变，汇总表可重建。grader 修订后保留旧结果并生成新评分，团队才能解释榜单变化来自系统还是仪器。

## “未评估”不是零分

环境失败、预算未运行、工具不兼容和拒绝提交分别代表不同缺失机制。把它们全部记为零会惩罚基础设施，把它们全部删除又会美化结果。报告应保留 `not_run`、`environment_error`、`invalid_output`、`graded_failure` 等状态，并公开各自数量。只有预注册规则能决定哪些进入主要分母。

## 双案例镜头

云舟零售的诊断集可以给“选对仓库但通知错误”部分分；资格集必须要求库存预留、订单状态、客户通知和禁止动作全部正确。星桥硬件的诊断集可以评价根因分析质量；DVT 放行资格必须要求安全测试证据、需求追踪和审批状态同时成立。

## 实践检查单

- 文档中每次出现“模型成绩”能否替换成完整系统配置？
- 研发可见题和资格隐藏题是否分开？
- 环境故障是否有独立状态，而非从分母删除？
- Leaderboard 是否把不同预算或工具条件放在同一列？
- 每个指标最终改变哪项决策？

## 练习：拆解一张排行榜

任选一张公开排行榜，补全它省略的八层信息。对无法找到的信息标记“未披露”，不要推测。最后写出三个该榜单能支持的结论和三个不能支持的结论。
