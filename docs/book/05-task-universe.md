# 从任务宇宙到可维护题集

> **本章问题**：怎样把现实世界中无限、动态的任务，变成有限但有代表性的 benchmark？

任务宇宙（task universe）就是目标部署中所有相关情况的总和。题集只是从这个总和里抽出的少量样本。很多团队一上来就看手头有什么数据，结果手头的数据反过来定义了“能力是什么”。更稳妥的顺序是：先从真实部署、业务决策和风险出发，确定必须观察哪些任务，再决定去哪里找样本。

本章的任务宇宙、频率集与风险集在全书证据链中的位置见[框架总览](/appendix/framework-map)。

## 建立任务分类，而不是堆案例

任务宇宙至少需要五个轴：

- 业务频率：日常高频、低频边界、罕见事故；
- 难度来源：知识、推理、工具、长程依赖、模态和协作；
- 状态条件：完整、缺失、矛盾、过期、并发和系统故障；
- 风险：可逆、需审批、不可逆、安全或合规关键；
- 人机关系：自主完成、建议人批准、必须升级和禁止处理。

分类不是为了做一张漂亮表格，而是为了找出遗漏。如果某个对部署很重要的格子没有任务，说明能力证据不完整；如果一批任务找不到对应的构念，它们可能只是在给结果增加无关噪声。

## 频率集与风险集必须分开

按生产频率抽样，适合估计日常价值；但少见的严重事故，会被平均数盖住。所以企业 benchmark 至少要维护两套题：频率集按真实发生率抽样，用来回答吞吐、质量和成本；风险集按严重程度、是否能撤回、以及攻击面抽样，用来回答系统能不能上线、能不能获得权限。

两套分数不能简单平均。数百个普通订单成功，不能抵消一次未经审批的高额退款；大量普通测试报告正确，也不能抵消一次安全证据缺失时的错误放行。

## 四条任务来源

第一条来源是领域专家根据真实工作产品原创。它能覆盖还没有出现在日志里的新要求，但也可能更像理想流程，而不是员工平时真正的做法。

第二条来源是生产事件、人工大改和事故。它最贴近真实工作，但必须先脱敏、去重，并重新写出可以执行检查的正确结果。

第三条来源是政策、FMEA（失效模式与影响分析）、红队测试和威胁模型。它很适合构造边界条件、抓危险捷径，但不能用来估计这类事件在生产中有多常见。

第四条来源是参数化合成。它能覆盖更多组合，也能控制某个因素的变化，但很容易生成现实里不会出现的“玩具题”。合成器本身也要经过领域专家审核，并和生产数据做分布对比。

健康题集混合四条来源，并保存来源标签，避免把对抗题权重误解成生产概率。

## 写出可独立判定的 Task Spec

一条任务至少要写清：稳定 ID、对应的构念、初始状态、系统能看到的输入、允许使用的工具、目标终态、禁止终态、升级条件、预算、grader、严重度、来源、版本和所属切分。开放任务还应该给出以行为为中心的 rubric（评分标准），并列出多种可接受路径，而不是只给一份“标准答案”。

正断言与负断言必须同时存在。创建采购单的任务不仅检查采购单存在，还要检查供应商、金额、审批正确，并确认没有重复单、错误库存修改和越权通知。

## 切分的真正单位

随机按行切分，常常会制造虚假的泛化。同一个客户、订单、产品、设备、文档模板或代码仓库的近似副本，可能同时出现在训练集和测试集。企业数据更应该按实体、时间、组织或生成模板分组；对会变化的政策，要保留“未来时间”切分；同一事故的多个版本，也要绑定在同一个集合里。

污染也不是简单的“题目全文有没有出现在训练数据里”。答案、解析、模板、衍生合成数据、评测 Skill，以及开发者围绕公开榜单反复调参，都会削弱测试独立性。可以用原创私有题、按时间切分、近重复检测、限制隐藏集提交次数、记录接触次数、滚动换题和锚题等值来降低风险。

## 动态题集如何保持可比

固定题集方便纵向比较，但会逐渐变得太容易，也更容易被污染；动态题集保持新鲜，却让不同时间的分数不能直接对比。一个折中办法是保留一组受保护的锚题，同时不断加入新题，再用一批重叠运行的系统或尺度模型把不同版本连起来。每次发布都要同时写明 suite 版本和具体改了什么。

坏题审计是常规治理。不可解、歧义、多个合理答案、grader 错误、环境初始化失败和答案泄漏都需要修订。修订后应回溯重评分历史系统，并明确榜单变化来自模型还是仪器。

## 从原始事件到资格任务的流水线

一条生产事件不能直接复制进题集。可以按这七步处理：第一，保存事实，包括输入、时间、版本、动作、终态和人工修复；第二，脱敏，删掉与构念无关的偶然细节；第三，重建一个最小环境，确认领域专家能独立完成；第四，写出正断言、负断言和严重度；第五，做几个近邻变化，检查系统是不是只靠记忆；第六，让 grader 分别测试合理正解、替代正解、近错解和危险捷径；第七，再决定它属于开发集、资格集、风险集还是事故集。

这个流程保留了事件的失败机制，又避免把客户标识、偶然文案和未来答案泄漏给候选。原始事件与合成任务之间要保存可审计映射，但访问权限可以不同。

## 参数化合成如何不生成“玩具题”

合成器应该从真实的约束关系出发，而不是随机拼接名词。参数之间往往有依赖：受监管商品可能不能拆单；器件封装会决定 PCB 是否兼容；客户等级会影响 SLA，但不能绕过隐私规则。

可以先定义一个只生成合法状态的程序，再一次只改变少数因素。每个组合都要检查必须始终成立的业务规则，还要随机抽样给专家盲审，看它是否像真实任务。最后，再比较合成数据和生产数据在关键特征上的分布。

合成任务最适合覆盖稀有组合、构造可控反事实和压力测试。它不应用来估计真实频率，也不能替代生产证据。

## 题目难度不是一个数字

Agent 任务的难度，可能来自步骤很长、依赖隐藏、工具不稳定、信息缺失、政策冲突、模态要求或风险限制。两个通过率同样低的任务，修复方法可能完全不同。因此目录要记录具体的难度构成，不要只贴一个 `hard` 标签。

试测后分析地板、天花板、任务级方差和失败类别。若所有系统都因环境错误失败，应修环境；若只有专家能解但彼此分歧，应修规范；若强系统通过但弱系统随机，才可能是有用区分题。

## 资格集访问是一种权限

隐藏题也要像权限系统一样管理。记录谁在什么时间、以什么目的接触了哪些题，得到的反馈是什么。研发只看到聚合后的失败类型，还是能看到每题 trace，会直接改变过拟合风险。团队反复失败、现场修改、继续提交，实际上已经把资格集用成了开发集。提前规定提交次数和换题策略，比事后说“我们没有训练”更可信。

## 双案例镜头

云舟零售的分类轴包含订单价值、客户等级、库存位置、承运事件、政策版本与是否需审批。星桥硬件包含研发阶段、需求安全等级、器件生命周期、测试证据状态、缺陷严重度和工程变更权限。两家公司都按实体和时间切分：同一订单族或同一缺陷/设计版本不能跨集合。

## 练习：构造 5×5 任务地图

选择两个最重要的分类轴，各分五档，形成 25 个格子。标出生产频率、严重度、现有样本数和 grader 可行性。不要立刻补齐所有格子；先解释哪些空白是合理边界，哪些是危险盲区。
