# Harness：被忽略的系统变量

> **本章问题**：模型相同，为什么换一个 Agent 产品后表现可能像换了代际？

Agent harness 是让模型进入行动循环的系统：系统指令、上下文装载、工具表示、记忆、规划、压缩、验证、恢复、重试、权限、沙箱与终止。它不是模型的包装皮肤，而是决定模型实际看见什么、何时得到反馈、能否修复错误的控制系统。

Model × Harness × Skill 的变量关系及其与其他框架的位置见[框架总览](/appendix/framework-map)。

::: info 来源事实 · Harness 交互
[SkillsBench v4](https://arxiv.org/abs/2602.12670) 在 18 个 Model×Harness 配置上观察到 Skill 增益从 +4.1 到 +25.7 个百分点不等。该数字不能把差异单独归因于 Harness，却直接说明 Skill 效果会随 Model×Harness 配置变化；因此报告 Skill lift 时必须披露并配对控制 Harness。完整实验结果与边界见[第 10 章](/book/10-skills#三组实证结果带来的正确问题)。
:::

在软件工程 Agent 中，仓库搜索、文件编辑、测试反馈和上下文压缩足以显著改变同一模型的 SWE-bench 表现。类似效应也存在于 Web、终端和企业任务。如果发布只写模型名，无法复现，也无法判断改进来自模型还是 Harness。

## Evaluation harness 与 Agent harness

Evaluation harness 装载任务、运行系统、收集轨迹并评分；Agent harness 决定被测 Agent 如何行动。两者边界必须清楚。若评测框架替系统自动修复参数、重试工具或补充上下文，它已经改变被测能力。

推荐为 Agent harness 建立 Harness Card，记录：基础指令语义、工具集合与 schema、观察表示、上下文预算、记忆、规划、并行、恢复、验证、停止、权限、依赖、版本和已知限制。

## 为什么“公平比较”有两种

比较模型时，想知道的是在相同系统条件下哪一个能力更强；比较产品时，想知道的是用户实际得到哪个组合更好。这两个问题需要双赛道。

**Locked-capability 赛道**固定 Agent harness、工具、环境、任务、预算与 grader，只更换模型。它增强内部效度，适合模型选型。

**Native-product 赛道**允许各产品使用推荐的原生 Harness 和公开最佳配置，但统一任务、环境、墙钟、总成本与安全边界。它增强生态效度，适合采购和产品比较。

把“模型 A＋产品 A”与“模型 B＋产品 B”的差值解释成模型差异，是完全混杂。反过来，把所有产品削成同一最低工具集，也会抹掉真实价值。

## Harness 的关键设计变量

上下文策略决定哪些文件、记录和历史进入模型；压缩可能保留结论却丢掉证据。工具语义决定模型看到高层业务动作还是底层 API。规划可以提高长程一致性，也会增加成本和错误承诺。验证循环能修复失败，也可能无限耗费预算。并行提高吞吐，却引入状态冲突。停止策略能避免循环，也可能过早宣布完成。

这些变量存在交互：同一种 Harness 可能特别适合一个模型族，却限制另一个。没有脱离模型的绝对最佳 Harness。

## Harness benchmark 应测什么

除严格任务成功外，还要测上下文效率、无效工具调用、循环、错误终止、恢复率、重复副作用、成本、尾延迟、人工接管、权限违规与可观测性。Harness 的目标不是让模型尽可能多做，而是在预算与风险下提高正确完成。

对 Harness 做消融时，一次只移除或替换一个机制：例如压缩、计划、验证、重试或高层工具。多 trial 配对结果能揭示机制在哪些任务上有帮助、在哪些任务上产生负作用。

## 可观测性是评测前提

若 Harness 只留下最终回答，失败无法归因。至少记录模型调用、工具调用、上下文摘要、状态变化、重试、错误、成本与终止原因。日志要避免泄露生产秘密，并保证候选系统不能篡改评测证据。

## 上下文策略怎样被单独评测

准备一组需要不同证据位置的任务：小文件关键行、跨文件依赖、旧结论与新证据冲突、超长日志尾部异常、权限隔离文档。固定模型和工具，只更换检索、排序、压缩与记忆策略。除成功率外，报告证据召回、无关 token、过期证据使用和压缩后可追溯性。

“装入更多上下文”未必更好。噪声会降低注意，成本增大，恶意内容攻击面扩大。一个好 Harness 不只是找到相关内容，还要保留来源、版本和冲突，并在不确定时回到原文。

## 工具抽象的公平困境

高层工具 `refund_order(order_id)` 隐藏身份、额度和幂等检查，能提高成功，却把一部分业务能力放进工具；低层工具要求 Agent 逐步操作，更能暴露计划，但增加无关语法负担。没有绝对公平的统一抽象。

报告工具提供的先验与安全保证。研究模型能力时，固定同一抽象；评产品价值时，允许原生抽象但把工具实现计入系统。对关键安全，不应故意移除确定性权限检查来“考模型”，生产防线与能力评测可以分层。

## 验证循环何时有害

Self-check、critic 和测试循环常提高质量，却可能形成同源盲点：同一模型重复确认自己的错误；也可能为通过窄 grader 投机，或在无新证据时无限循环。评测验证机制需要区分有信息增益的检查和重复表达。

记录每次验证引用的新证据、修正类型和成本。设置最大循环和退化检测。构造 grader 漏洞题检查 critic 是否只迎合测试。高风险任务可让独立 verifier 或规则承担关键不变量。

## Harness 发布也需要回归

上下文压缩、工具 schema、重试和停止的任何修改都可能跨全部任务产生系统性故障。Harness 回归不仅跑功能测试，还应运行代表任务矩阵，检查成本尾部、权限和 trace 完整。Harness 版本应与模型升级分开发，避免无法归因。

## 双案例镜头

云舟零售的 Harness 包含政策检索、订单工具、写前复核和高风险升级。星桥硬件的 Harness 包含工件索引、需求—测试追踪、变更影响分析和阶段门禁。相同模型可能在第一套高层业务工具中表现很好，却在第二套长文档和证据图中受上下文策略限制。

## 练习：一页 Harness Card

为你的系统写出上下文、工具、规划、验证、恢复、权限、停止和预算八项配置。再设计一个 locked-capability 对照，回答如果分数变化，你能把它归因到哪个机制。
