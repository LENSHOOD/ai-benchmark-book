# Harness：同一个模型为什么像换了一个员工

> **本章问题**：模型没有变，为什么换一个 Agent 产品，表现却可能差一代？

先说答案：模型不会独自工作。它看到哪些资料、能用什么工具、失败后会不会重试、什么时候停下来，都由外面的运行框架决定。这个框架通常叫 **Harness**。

Harness 包括系统指令、上下文装载、工具说明、记忆、计划、压缩、验证、恢复、权限和沙箱。它不是一层好看的包装，而是 Agent 的工作台。同一个模型放在不同工作台上，做事方式当然会变。

Model × Harness × Skill 的关系见[框架总览](/appendix/framework-map)。

::: info 来源事实 · 不同 Model×Harness 组合的 Skill 效果不同
[SkillsBench v4](https://arxiv.org/abs/2602.12670) 测了 18 种 Model×Harness 组合。加入 Skill 后，不同组合的提升从 +4.1 到 +25.7 个百分点不等。这个结果不能证明差异只来自 Harness，但能证明一件事：报告 Skill 效果时，必须把模型和 Harness 一起写清楚。完整数据和边界见[第 10 章](/book/10-skills#两组实证结果带来的正确问题)。
:::

软件工程 Agent 是最直观的例子。仓库怎么搜索、文件怎么修改、测试结果怎么反馈、长对话怎么压缩，都会改变 SWE-bench 成绩。Web、终端和企业流程也一样。发布报告如果只写模型名，别人既无法复现，也不知道提升来自哪里。

## Evaluation harness 与 Agent harness

这里有两个容易混淆的东西。

- **Evaluation harness** 是“考场”：装题、启动系统、保存过程并打分。
- **Agent harness** 是“工作台”：决定 Agent 怎样找资料、调用工具、检查和重试。

如果考场替 Agent 修参数、补资料或自动重试，它就不只是观察者了，而是在帮忙答题。边界必须写清楚。

建议为 Agent harness 建一张 Harness Card。至少记录：基础指令、工具和参数格式、上下文预算、记忆、规划、并行、验证、恢复、停止、权限、依赖、版本和已知限制。

## 为什么“公平比较”有两种

先问清楚：你想比较模型，还是比较产品？

比较模型时，用 **Locked-capability 赛道**。固定 Harness、工具、环境、题目、预算和评分器，只换模型。这样更容易判断模型本身的差异。

比较产品时，用 **Native-product 赛道**。允许每个产品使用自己的最佳配置，但统一任务、环境、总时间、总成本和安全边界。这样更接近用户实际买到的东西。

“模型 A＋产品 A”对“模型 B＋产品 B”，只能说明两个完整组合不同，不能把差距全算在模型头上。反过来，把所有产品都砍到同一套最低配工具，也会把产品真实价值一起砍掉。

## Harness 的关键设计变量

Harness 主要在七个地方改变结果：

1. **上下文**：给模型看哪些文件、记录和历史；
2. **工具**：提供高层业务动作，还是底层 API；
3. **计划**：先列步骤，还是边做边想；
4. **验证**：完成后是否查数据库、跑测试或找独立证据；
5. **恢复**：调用失败、响应丢失或部分写入后怎么办；
6. **并行**：是否让多个动作同时发生，以及如何处理冲突；
7. **停止**：何时算完成，何时应该求助。

这些变量会互相影响。某种上下文压缩可能适合一个模型，却让另一个模型丢失关键证据。因此不存在脱离模型和任务的“最佳 Harness”。

## Harness benchmark 应测什么

不能只看任务最后过没过。还要看：浪费了多少上下文，是否反复调用同一工具，有没有死循环，失败后能否恢复，是否重复写入，成本和尾延迟多高，何时交给人，以及有没有越权。

做消融实验时，一次只改一个机制。例如只关掉压缩、计划、验证、重试或高层工具。对同一批任务运行多次，再看这个机制在哪些题上有帮助，在哪些题上反而添乱。

## 可观测性是评测前提

如果系统只留下最终回答，失败后只能猜。至少要保存：模型调用、工具调用、关键上下文来源、状态变化、重试、错误、成本和停止原因。

日志本身也要受保护。它不能泄露生产秘密，也不能让候选系统改掉自己的“考试录像”。

## 上下文策略怎样被单独评测

准备几类题：关键事实藏在小文件里；答案要跨多个文件拼起来；旧结论和新证据冲突；异常只出现在超长日志尾部；某些文档不该被当前用户看到。

固定模型和工具，只更换检索、排序、压缩和记忆方法。除了成功率，还要看是否找到了正确证据、塞入了多少无关内容、用了多少过期资料，以及压缩后还能不能追到原文。

上下文不是越多越好。噪声会分散注意力、增加成本，也会扩大提示注入的攻击面。好的 Harness 不只会找资料，还会保留来源和版本，发现冲突时回到原文。

## 工具抽象的公平困境

高层工具 `refund_order(order_id)` 可能已经包好了身份、额度和幂等检查。Agent 更容易成功，但一部分能力其实来自工具。低层 API 更能暴露 Agent 的计划能力，却会增加很多和业务无关的参数工作。

没有一种工具层级对所有问题都公平。研究模型能力时，固定工具抽象；比较产品价值时，把工具实现算进完整系统。对于权限和安全，不要为了“考模型”故意拆掉确定性防线。

## 验证循环何时有害

自检、批评者和测试循环经常有用，但也可能反复确认同一个错误。它们还可能只学会迎合一个有漏洞的评分器，或者在没有新证据时一直烧预算。

每轮验证都应说明：新看到了什么证据、修了什么、花了多少。设置最大循环次数和退化检查。关键安全条件最好交给独立规则或验证器，不要只让同一个模型再想一遍。

## Harness 发布也需要回归

改一个工具参数名、压缩规则或重试策略，可能让所有任务一起出问题。发布 Harness 时，不只跑功能测试，还要跑代表任务矩阵，检查成本尾部、权限和日志完整性。

Harness 与模型最好分开升级、分开版本化。否则分数变了，你很难知道是谁造成的。

目录变大也算一次变更。模型和旧工具都没改，只是加了一批新工具或 Skill，系统也可能选错、漏找，导致旧任务退步。因此每次扩展都要同时跑旧任务和新增任务，分别报告能力保留与新能力表现。

::: info 来源事实 · EvoHarnessBench
[EvoHarnessBench v2](https://arxiv.org/html/2609.04280v2) 于 2026 年 9 月 10 日更新，初版为 9 月 3 日。作者用 17 条分阶段扩展流、802 个独立任务，观察工具、Skill 和协作 Agent 增加后系统是否仍能完成旧工作。全文另列 1,510 个按评测轴展开的样本，不能与独立任务数混用。

它区分不带阶段间学习的部署评测，以及携带记忆等持久产物的自演化评测。前者看环境扩展的影响，后者还看经验能否继续适用。它提供了给回归测试增加时间轴的方法；这些是作者的实验设置与结果，本书未独立复跑。
:::

在自己的项目里，保存每一阶段的工具目录、Skill 版本、记忆状态和预算。旧题下降时，先查“没找到原工具”还是“找到却做错”，不要只用最终总分解释升级是否成功。

## 双案例镜头

云舟零售的 Harness 负责查政策、操作订单、写前复核和高风险升级。星桥硬件的 Harness 负责索引研发工件、追踪需求与测试、分析变更影响和检查阶段门禁。

同一个模型可能很会用零售里的高层业务工具，却在硬件项目的长文档和证据关系中迷路。这不是矛盾，只是工作台不同。

## 练习：一页 Harness Card

为你的系统写清八件事：上下文、工具、规划、验证、恢复、权限、停止和预算。然后设计一个只改变其中一项的对照实验。看到分数变化时，你应该能说清是哪项机制起了作用。
