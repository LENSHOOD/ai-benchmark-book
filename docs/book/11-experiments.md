# 实验设计、统计与因果归因

> **本章问题**：当候选系统高了 3 个百分点，怎样知道提升真实、重要，而且来自预期组件？

Benchmark 分数是样本上的观测，不是无误差能力值。任务抽样、模型随机性、环境波动、grader 和基础设施都会产生方差。更大的陷阱是混杂：模型、Harness、Skill 与预算一起变化，团队却把全部差异归给一个组件。

## 从任务级配对开始

比较两个候选时，让它们运行同一任务、同一初始状态和可比预算，分析每题差值，而不是两个独立总体均值。配对能抵消任务难度差异，提高检验能力，并允许逐题检查胜负来自哪里。

二元结果可报告配对胜/负/平、pass-rate delta 与区间；连续结果报告差值分布和稳健统计。只有总均值而没有逐题结果，无法发现系统在关键任务上的退化。

## 多 trial 处理非确定性

每个系统—任务组合运行多次，记录种子、服务端版本、推理配置、时间、工具错误和停止原因。先估计任务内方差，再看任务间方差。任务少而 trial 多，不能代替任务覆盖；任务多但每题一次，也无法看出不稳定。

真实服务中 trial 可能相关。共同政策、共享缓存、服务故障和同一上下文策略会让失败成簇。高风险场景不能只使用独立同分布假设，应辅以故障注入、分层重采样和情景分析。

## Model × Harness × Skill 全交叉

理想设计在同一批任务上交叉多个模型、Harness 和 Skill：

```text
outcome ~ model + harness + skill
        + model:harness + model:skill + harness:skill
        + task random effect
```

主效应回答平均影响，交互回答某机制是否只适合特定组合。若矩阵缺格，例如某模型只能运行原生产品，只能描述部署组合，不能声称已分离因果。

预算也是处理变量。一个系统通过更多重试提高成功，另一个早停降低成本，它们不是同一实验条件。可分别运行固定预算能力赛道和成本约束价值赛道，但不要把不同预算分数放在同一列。

## 区间、效应量与实际重要性

样本大时微小差异也可统计显著，样本小时重要差异可能不显著。发布前应定义最小实际重要差异（minimum practically important difference），同时报告绝对提升、相对提升、置信区间和业务含义。

两层 bootstrap 是直观默认：先重采样任务，再在任务内重采样 trial，保持聚类结构。复杂数据可用混合效应模型；正文不要求读者手算，重要的是模型与数据生成过程一致。

## 预注册与停止规则

在资格集运行前写下：候选版本、任务版本、样本、trial、预算、指标、veto、缺失值、环境失败、区间方法、通过阈值和最大重提次数。看到结果后继续微调并反复提交，会把资格集变成开发集。

探索可以自由，但探索结果要标注。确认性结论需要预注册和独立复现。

## 成本和业务价值

成本至少包括模型调用、工具、计算、墙钟、人工复核、集成、失败恢复和事故损失。只看 token 账单会低估真实成本。

可以报告单位严格成功成本：

```text
cost_per_strict_success = total_operating_cost / strict_success_count
```

业务净价值还要扣除错误期望损失。自动化率也不能单独看：高升级率可能伪装安全，高自治率可能伪装效率。自主完成、正确升级和错误自主应并列。

## 样本量从决策风险反推

不存在所有 benchmark 通用的“至少 100 题”。样本量取决于基线成功率、想检测的最小差异、任务方差、配对相关和风险容忍。与其先算一个精确数字，不如先做 20–30 题 pilot，观察任务间与 trial 内方差，再估计需要多少独立任务。

对罕见 veto，普通随机样本几乎看不到。风险集采用定向抽样和压力测试，不用频率置信区间伪装生产发生率。若目标是证明风险低于极小阈值，通常还需要安全论证、形式化约束和生产监控，不能靠有限“零事故”宣布安全。

## 顺序实验与早停

昂贵 Agent eval 可以分阶段：先跑便宜诊断淘汰明显差候选，再在共同任务上增加 trial，最后进入专家和风险集。早停规则必须预注册，例如明显触发 veto、成本超限或后验胜率达到门槛。看到短期领先就临时停止会产生赢家偏差。

自适应分配可以把更多预算给差异不确定的任务，但最终报告要说明采样机制，并用合适权重恢复目标分布。

## 交互图比一张系数表更有解释力

全交叉结果先画任务级差值和 Model×Harness、Model×Skill 交互。若 Skill 只帮助 basic 模型而限制 capable 模型，平均主效应接近零，却是关键产品结论。若 Harness 在长程任务增益大、简单任务只增加成本，应按任务路由，而不是全局启用。

统计模型用于压缩证据，逐题 trace 用于解释机制，两者缺一不可。

## 复现实验需要保存什么

保存代码与配置还不够。记录模型快照、服务端日期、Prompt、工具 schema、环境镜像、随机种子、预算、重试、依赖、grader、原始输出、缺失和人工仲裁。外部 API 无法完全冻结时，运行锚点系统监测服务漂移。

将 manifest 与结果一起发布。任何汇总表都应能从不可变逐 trial 数据重建，避免手工表格成为最终真值。

## 一个完整结果叙事

先说明决策与协议，再给主要差异和区间；随后展示任务切片、成本与风险；再分析组件交互和失败；最后写适用边界、负结果和下一步。不要以“候选提升 3.2%”开头后把条件埋在附录。一个诚实结论可以是“在低风险订单和固定预算下更好，但硬件风险集样本不足，不建议扩大权限”。

## 双案例镜头

云舟零售比较两个模型、两个 Harness 和有/无供应链 Skill，每格多 trial，并按订单价值分层。星桥硬件使用相同矩阵，但随机效应还包括研发阶段和工件族，veto 事件独立报告。两者都预先规定 critical task 不允许负增益。

## 练习：写实验预注册

选两个候选系统，为 30 个任务写一页预注册：配对方式、trial、预算、主要指标、最小重要差异、veto、环境故障处理和停止规则。再列出看到结果后你最想改、但不能改的三件事。
