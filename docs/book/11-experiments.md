# 实验设计：别把“看起来更好”当成证据

> **本章问题**：候选系统高了 3 个百分点，这个提升是真的吗？值得发布吗？又是谁带来的？

一个分数只是这批题、这次运行和这套评分规则下的观察。换题、换随机种子、换环境或换评分器，数字都可能变。更常见的问题是：模型、Harness、Skill 和预算一起变了，团队却把所有提升都归给模型。

本章不要求你堆统计术语。目标是让每个结论都有对照、有范围、能复查。

## 从任务级配对开始

比较 A 和 B 时，让它们做同一批任务，从相同初始状态出发，并使用可比预算。然后看每一道题的差，而不只是比较两个总平均分。

这样做叫**配对比较**。它能减少“这批题刚好更难”造成的干扰，也能让你看见 A 赢在哪些题、又输在哪些题。

二元结果至少报告胜、负、平、通过率差和区间。连续分数则报告逐题差值。只有总分，没有逐题结果，关键任务退步很容易被平均数藏起来。

## 多 trial 处理非确定性

**Trial** 就是同一个系统做同一道题的一次运行。每个组合最好跑多次，并记录随机种子、模型版本、推理配置、时间、工具错误和停止原因。

题很少、每题跑很多次，不能补上任务覆盖不足。题很多、每题只跑一次，也看不出系统是否稳定。两种变化都要看。

真实服务里的失败还可能一起发生。例如大家共享同一政策、缓存或服务故障。遇到高风险任务，除了普通统计，还要做故障注入、按事件分组重采样和情景分析。

## Model × Harness × Skill 全交叉

如果你想知道提升来自哪里，尽量在同一批任务上交叉不同模型、Harness 和 Skill：

```text
outcome ~ model + harness + skill
        + model:harness + model:skill + harness:skill
        + task random effect
```

主效应回答“平均来说有没有帮助”，交互项回答“它只对哪些组合有帮助”。如果某个模型只能跑在自己的原生产品里，你只能比较完整产品，不能声称已经分离了模型影响。

预算也必须算作实验条件。一个系统靠更多重试提高成功，另一个为了省钱提前停，它们不是同场考试。可以分别做固定预算的能力赛道和成本受限的价值赛道，但不要混在一列里。

## 区间、效应量与实际重要性

样本很大时，极小差异也可能“统计显著”；样本很小时，真正重要的差异又可能没有显著。发布前先定义**最小实际重要差异**：变化多大才值得换系统或承担迁移风险。

报告时同时给绝对变化、相对变化、区间和业务含义。例如“提升 2 个百分点”还不够，要说明它相当于每月多正确处理多少订单、少花多少人工分钟，或减少哪类事故。

两层 bootstrap 是常用做法：先重采样任务，再在任务内部重采样 trial。数据更复杂时可用混合效应模型。公式不是重点，重点是统计方法要跟真实的数据生成方式一致。

## 预注册与停止规则

在看资格集结果前，先写下：候选版本、任务版本、样本、trial 数、预算、指标、红线、缺失值处理、环境失败处理、区间方法、通过标准和最大提交次数。

看到结果后继续改 Prompt，再反复提交同一资格集，会把“考试题”变成“练习题”。探索当然可以，但要标成探索。要支持正式发布，最好用事先写好的规则和未参与调参的数据。

## 成本和业务价值

成本不只是 token 账单。还包括工具、计算、等待时间、人工复核、集成、失败恢复和事故损失。

可以先算每次严格成功的成本：

```text
cost_per_strict_success = total_operating_cost / strict_success_count
```

但它仍不是完整价值。错误自主可能比多次人工升级贵得多。因此自主完成、正确升级和错误自主必须分开报告。

## 样本量从决策风险反推

没有“所有 benchmark 至少 100 题”这种通用答案。需要多少题，取决于当前成功率、你想看出的最小差异、任务之间有多不一样，以及错误决定的代价。

务实做法是先用 20 到 30 题试跑，观察题目之间和多次运行之间的波动，再估算正式样本。

罕见但严重的风险不能只靠随机抽样。要专门建立风险集和压力测试。有限样本里一次事故都没有，也不能证明系统安全。

## 顺序实验与早停

Agent eval 很贵，可以分阶段花钱。先用便宜诊断淘汰明显不合格的候选，再给剩余候选增加 trial，最后才上专家评审和高风险任务。

早停规则要提前写。例如触发严重红线、成本超限，或证据已经足以做决定。看见某个候选暂时领先就临时停，会偏向“早期赢家”。

如果系统会把更多预算投给“更有希望”或“更难判断”的候选，报告必须写清分配规则。汇总时还要用权重还原原本想代表的任务分布。否则，跑得更多的候选会在结果里占据过大分量。

## 交互图比一张系数表更有解释力

先画逐题差值，再画 Model×Harness、Model×Skill 的交互。你可能发现某 Skill 只帮助较弱模型，却限制较强模型；也可能发现 Harness 只在长任务中有用，简单任务里只是更贵。

这些结论会直接改变产品策略：按任务路由，而不是全局开启。统计模型负责压缩规律，逐题轨迹负责解释原因，两者都要保留。

## 复现实验需要保存什么

除了代码和配置，还要保存模型快照、服务日期、Prompt、工具参数格式、环境镜像、依赖、随机种子、预算、超时、重试、原始输出、状态快照、评分器版本和缺失原因。

给每次运行一个不可变 ID。摘要表应能追到每条原始记录。不能只保存“最好的一次”。

外部模型 API 往往不能完全冻结。可以固定一组锚点任务，定期用同一协议重跑。锚点结果突然变化时，先检查服务是否漂移，再解释候选系统的升降。

发布结果时，也要发布记录文件版本和哈希的 manifest。任何汇总表都应能从不可变的逐 trial 数据重建，不能让手工表格成为最终真值。

## 一个完整结果叙事

好的报告不是一句“新系统提升 8%”。它应说明：比较了什么；哪些条件被固定；哪些条件改变；用了多少任务和 trial；平均变化多大；区间多宽；哪些关键题变差；成本和人工接管怎么变；有没有触发红线；这个证据支持什么决定，又不支持什么决定。

## 双案例镜头

云舟零售要同时看普通异常和高损失风险。星桥硬件要按研发阶段和缺陷严重度分层。两边都要先做任务级配对，再看 Harness 和 Skill 的交互，最后把差异翻译成钱、时间、风险和人工负担。

## 练习：写实验预注册

选择两个系统，写一页预注册。必须包含主要比较、任务切分、trial 数、预算、缺失处理、红线、最小重要差异、早停规则和发布条件。写完后再看结果。
