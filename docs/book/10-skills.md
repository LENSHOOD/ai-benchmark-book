# Skill/Plugin：怎样证明“工作说明书”真的有用

> **本章问题**：把 SOP、示例和脚本装进 Skill 后，怎样证明它真的帮了忙？

可以先把 **Skill** 理解成“给 Agent 的工作说明书和工具包”。它可能包含步骤、示例、脚本、参考资料、工具连接和检查规则。Plugin、上下文包等形式虽然名字不同，也常在做类似的事。

Skill 不等于一段更长的 Prompt。真实系统要先找到它、选中它、读懂它，再按要求执行和检查。任何一步出错，Skill 都可能没帮助，甚至帮倒忙。

## Skill 的七段行为链

七段链与 Oracle/Retrieval/Open 三种实验条件在全书中的位置见[框架总览](/appendix/framework-map)。

1. **发现**：系统知道这项 Skill 存在；
2. **选择**：在多个候选中选对；
3. **加载**：真正读到了需要的文件和脚本；
4. **理解**：知道规则如何用于当前任务；
5. **执行**：按流程调用工具；
6. **验证**：检查结果，发现失败；
7. **协同**：遇到其他 Skill、系统规则或环境限制时会处理冲突。

只看最终通过率，你不知道问题出在哪一步。因此 Skill eval 不只记录成败，还要记录是否触发、加载了什么、有没有照着关键流程做、花了多少成本，以及每道题到底提升还是退步。

## 三组实证结果带来的正确问题

::: info 来源事实 · SB-2026 / SWSB-2026
[SkillsBench v4](https://arxiv.org/abs/2602.12670) 在 87 个任务、8 个领域和 18 种 Model×Harness 组合上做了配对实验。人工策划的 Skill 把平均通过率从 33.9% 提高到 50.5%，平均提升 16.6 个百分点。不同组合的提升从 +4.1 到 +25.7 个百分点。它证明的是“有些精心设计的 Skill 对某些组合有效”，不是“Skill 天然有效”。

[SWE-Skills-Bench](https://arxiv.org/abs/2603.15401) 提供了反例。在 49 个公开软件 Skill、约 565 个实例和 6 个子领域中，39 个 Skill 没有提高通过率，平均只提升 1.2%。3 个版本不匹配的 Skill 最多让成绩下降 10%，token 用量最高增加 451%。这些数字只适用于论文的实验条件，不能直接套到其他行业。
:::

::: tip 综合判断
两组结果并不冲突。Skill 有没有用，取决于任务是否匹配、模型和 Harness 是否合适、系统能否找到正确版本，以及多个规则会不会打架。平均提升也可能盖住关键任务上的严重退步。
:::

## 最小实验矩阵

::: warning 实践建议
至少测五种情况：不用 Skill；使用完整 Skill；拿掉关键模块；提供过期或冲突 Skill；提供无关或恶意 Skill。资源够时，再换不同模型和 Harness。题目、环境和预算要保持可比。
:::

最直观的指标是同一道题前后的差：

```text
lift(task) = score(with_skill, task) - score(no_skill, task)
```

不要只报平均 lift。还要报多少任务变差、关键任务最坏下降多少、成本如何变化、工具调用是否变多，以及有没有触发安全红线。

## Skill grader 不应只检查“是否引用”

Skill 的目标是让行动变好，不是让模型在回答中背诵说明书。

可以分五层检查：有没有找到和加载；关键步骤有没有执行；业务状态是否真的正确；成本和安全是否合格；生产中是否误触发或经常被人改掉。

模型没有说“我使用了某 Skill”，但做对了事，仍可能有效。反过来，它逐字复述 SOP，却把订单改错了，就不该得分。

## 生命周期与供应链安全

Skill 至少要有名称、版本、适用的模型和 Harness、依赖、权限、数据范围、生效条件、来源、测试和回滚方法。政策或工具更新后，旧 Skill 要重新验证。

外部 Skill 可能带脚本、参考材料和工具连接。它既是知识资产，也是潜在的提示注入和软件供应链入口。默认给最小权限，不要因为“只是文档”就直接信任。

## 发现与选择应独立成 benchmark

有些测试把正确 Skill 的路径直接塞进 Prompt。这样只测了“给到手后会不会照做”，没有测产品能否找到它。

可以分三层：

- **Oracle condition**：直接给正确 Skill，单测内容质量；
- **Retrieval condition**：从真实目录里选择，测试发现和描述；
- **Open condition**：允许多个 Skill 一起工作，测试冲突和编排。

三层之间的差距能帮你找原因。Oracle 高而 Retrieval 低，先修命名、描述和索引；Retrieval 高但结果低，问题在内容或执行；单个 Skill 好、组合后差，问题在冲突处理。

## 过期知识不总能靠日期解决

很多规则没有统一失效日。它可能只适用于某个产品版本、地区、客户等级或工具参数格式。系统必须同时看任务条件和 Skill 的适用范围。

测试时放入同名旧版本、只对部分地区有效的规则，以及来源不可信的材料。正确行为有时不是“自动选最新”，而是停止并交给人确认。

## 模块消融如何指导维护

把 Skill 拆成流程、示例、脚本、参考资料和验证器。每次拿掉一块，再看成功率、成本和风险。

如果删掉示例没有影响，它可能只是在占上下文。如果真正有用的只有验证器，可以考虑把它上移到 Harness 或工具层。如果脚本提速但扩大了权限，就单独设门禁。消融的目的不是证明每一块都有用，而是敢于删掉没用的东西。

## 生产中的 Skill 指标

离线通过只是开始。上线后还要看：应该触发时有没有触发、不该触发时是否误触发、大家实际用了哪个版本、用户是否经常关闭或改写、成本是否增加，以及哪些任务出现负增益。

用户总绕过某个 Skill，通常不是“用户不会用”，而是流程可能不适合真实工作。把这些情况做成下一版任务，不要只改几句文案。

## 双案例镜头

云舟零售的 Skill 包含替代仓、受监管拆单、退款审批和通知流程。星桥硬件的 Skill 包含器件替代、测试证据、FMEA 检查和阶段门禁。

两边都要测试旧政策和旧规格。系统要能说“这份说明不适用”，而不是看到文档就盲从。

## 练习：设计负增益测试

选一个现有 Skill，准备正常、边界、过期、冲突和无关五类任务。先写清楚：即使普通成功率上升，出现什么情况也必须阻止发布。然后分别移除示例、脚本和验证模块，观察变化。
