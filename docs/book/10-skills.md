# Skill/Plugin：作为可验证干预

> **本章问题**：把 SOP、示例和脚本封装成 Skill 后，怎样证明它真的帮助了系统？

Skill、Plugin、上下文包和类似机制把程序性说明、示例、脚本、参考资料、工具连接和验证规则聚合起来，解决“在特定领域怎样做”。它们不是更长的 Prompt，而是 Agent 系统中可发现、选择、加载、执行、验证和更新的依赖。

这种资产看起来必然有帮助：更多相关知识为什么会变差？现实中，Skill 可能没有被发现，被错误选择，与模型已有策略冲突，包含过期版本，挤占上下文，诱导冗长路径，甚至引入恶意脚本和权限扩大。因此 Skill 必须被视为可验证干预。

## Skill 的七段行为链

七段链与 Oracle/Retrieval/Open 三条件在全书中的位置见[框架总览](/appendix/framework-map)。

1. **发现**：系统知道存在这项 Skill；
2. **选择**：在多个候选中选对；
3. **加载**：读取了需要的说明、文件和脚本；
4. **理解**：将规则映射到当前任务；
5. **执行**：按流程使用工具；
6. **验证**：运行检查并识别失败；
7. **协同**：处理其他 Skill、系统策略与环境规则的冲突。

只看最终通过率无法说明失败位于哪一段。Skill eval 应分别记录触发、加载、流程遵循、结果、效率、安全和任务级增益。

## 三组实证结果带来的正确问题

::: info 来源事实 · SB-2026 / SWSB-2026
[SkillsBench v4](https://arxiv.org/abs/2602.12670) 在 87 个任务、8 个领域和 18 个 Model×Harness 配置上做配对实验：人工策划 Skill 将平均通过率从 33.9% 提高到 50.5%，即 +16.6 个百分点；不同配置的提升为 +4.1 至 +25.7 个百分点。该结果证明“某些策划良好的 Skill 在某些配置上有效”，而不是证明 Skill 天然有效。

[SWE-Skills-Bench](https://arxiv.org/abs/2603.15401) 给出重要反证：49 个公开软件 Skill、约 565 个实例和 6 个子领域中，39 个 Skill 的通过率提升为零，平均增益只有 +1.2%；3 个版本错配的 Skill 最多使成绩下降 10%，token 开销最高增加 451%。这些数字来自论文摘要所报告的实验条件，不能直接外推到其他领域或产品。
:::

::: tip 综合判断
两组结果并不矛盾。重要结论不是“Skill 有效”或“Skill 无效”，而是效应取决于任务分配、领域匹配、模型、Harness、发现机制和版本。平均正增益会掩盖关键任务负增益；单一软件领域中的弱平均效应，也不能否定其他领域中精心策划资产的收益。
:::

## 最小实验矩阵

::: warning 实践建议
至少运行五个条件：无 Skill；完整 Skill；移除关键模块的消融；过期/冲突 Skill；无关或恶意 Skill。若资源允许，再交叉多个模型与 Harness。任务和环境必须相同，多 trial 记录交互。这是本书建议的最小诊断矩阵，不是外部标准规定的固定赛制。
:::

核心量是任务级配对增益：

```text
lift(task) = score(with_skill, task) - score(no_skill, task)
```

报告平均 lift 之外，还要给负增益比例、critical task 最坏 lift、成本变化、工具调用和安全 veto。发布规则不能只看平均为正。

## Skill grader 不应只检查“是否引用”

Skill 的目标是改变行动质量，而不是让模型在回答中复述说明。第一层检查发现和加载；第二层检查必要流程不变量；第三层检查业务终态；第四层检查效率和安全；第五层观察生产使用率、错误触发和人工纠正。

一个 Skill 即使从未被显式引用，只要通过工具和流程产生正确结果，仍可能有效；反之，逐字复述 SOP 却执行错误，不应得分。

## 生命周期与供应链安全

Skill 需要名称、版本、适用模型/Harness、依赖、权限、数据域、生效期、来源、签名、测试和回滚。生产政策更新后，旧 Skill 应触发复证。对外部 Skill 的脚本、参考材料和工具连接采用最小权限，防止把知识资产变成提示注入和软件供应链入口。

## 发现与选择应独立成 benchmark

有些实验把正确 Skill 路径直接放入 Prompt，测到的是“给定 Skill 后能否遵循”，没有测实际产品中的发现。完整评测可以分三层：oracle condition 直接提供正确 Skill，隔离内容质量；retrieval condition 从真实目录选择，测发现和描述；open condition 允许组合多个 Skill，测冲突与编排。

三层差值能定位瓶颈。若 oracle 高而 retrieval 低，应优化命名、描述和索引；若 retrieval 高但结果低，问题在执行或内容；若单 Skill 高而开放组合低，问题在冲突和编排。

## 过期知识不总能靠日期解决

Skill 可能没有明确失效日，而是只对某产品版本、地区、客户层级或工具 schema 有效。任务上下文与 Skill manifest 要能做适用性匹配。冲突规则应说明系统策略、法律政策、企业规则、团队惯例和示例之间的优先级。

评测要构造同名旧版本、局部适用规则和来源不可信三种条件。正确系统可能拒绝使用并升级，而不是总能自动选择新文件。

## 模块消融如何指导维护

将 Skill 拆成流程、示例、脚本、参考和 verifier。分别移除模块，观察通过、成本和风险。若示例移除不影响结果，它可能是上下文负担；若 verifier 是唯一产生增益的模块，应将关键检查上移到 Harness 或工具；若脚本提高效率却增加权限，需要单独门禁。

消融不是为了证明每一段都有价值。发现冗余并删除，是 Skill 工程成熟的标志。

## 生产中的 Skill 指标

离线通过后还要看触发率、未触发、误触发、版本分布、人工关闭、错误引用、执行成本和生产负增益。用户绕过 Skill 或经常手动改写，可能说明流程不适合真实工作。监控结果进入下一版任务，而不是只优化文档措辞。

## 双案例镜头

云舟零售的 Skill 注入替代仓、受监管拆单、退款审批和通知流程。星桥硬件的 Skill 注入器件替代规则、测试证据要求、FMEA 检查和阶段门禁。两者都要加入“旧政策/旧器件规格”条件，证明系统能识别不适用资产，而不是盲从。

## 练习：设计负增益测试

选择一个现有 Skill，构造正常、边界、过期、冲突和无关五类任务。定义什么情况下 Skill 即使提高普通成功率也必须阻断发布。然后写出移除示例、脚本和验证模块的三项消融。
