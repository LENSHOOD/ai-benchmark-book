# 从心理测量到动态 Agent Eval

> **本章问题**：今天关于污染、饱和、Judge 和排行榜的争论，历史上从哪里来？

AI benchmark 看起来很新，其实借用了很多老方法：心理测量、统计推断、科学实验、软件测试和竞赛制度。了解这段历史，不是为了背诵每个项目是哪年发布的，而是为了看清两件事：每种新方法解决了什么问题，又留下了什么新问题。

::: tip 综合判断 · 历史叙事口径
下面的七个阶段，是本书为了讲清测量问题所做的整理，并不是学界公认的唯一分期。项目年份和原始主张可在章末的一手来源中核对；“解决了什么、留下什么设计债”是本书采用的解释方法。
:::

## 第一阶段：不可见能力如何被测量

人的智力、知识和人格看不见、摸不着，只能通过一些行为来推测。心理测量因此留下了几条今天仍然重要的经验：测得稳定，不等于测得正确；题目多，不等于覆盖全面；一个分数只有说明用途、对象和条件，才有意义；测量误差也不会在数据清洗后自动消失。

项目反应理论（Item Response Theory，简称 IRT）又把题目难度、区分能力和猜对的可能性放进模型。它提醒我们：benchmark 里的每道题并不一样有用。某些题适合区分能力较弱的系统，另一些题才适合区分强系统。今天用 IRT 校准语言模型题集时，仍要检查它依赖的假设，例如题目是否主要测同一种能力、题目之间是否相对独立。否则，得到的刻度虽然复杂，却可能仍然测错了东西。

## 第二阶段：图灵把本体问题转成行为协议

1950 年，图灵没有硬答“机器到底会不会思考”，而是设计了模仿游戏，把哲学问题变成可观察的人机对话。这也定下了 AI 评测的一种基本做法：内部能力看不见时，就设计一套行为规则，从表现中收集可以比较的证据。

这套做法也有明显边界。评测规则允许我们看什么，我们就只能看到什么；行为相似，不代表内部机制相同；测试者和被测对象都会逐渐适应规则。今天的静态问答、Arena 偏好对比和 Agent 沙箱，都沿用了这个基本结构。

## 第三阶段：数据集与 shared task 建立可比性

UCI 数据集、TREC 信息检索评测和 CoNLL shared task（共同任务）让研究者开始使用同一份数据、相同切分、相同指标和统一截止时间。大家不再各自挑最好看的演示，而是能在相同条件下比较，进步也可以逐年积累。软件工具、隐藏测试和共同维护任务的社区，也从此成了 benchmark 的一部分。

代价也随之出现。人们容易把数据集当成整个真实任务；一个指标会把多种质量压成一个数字；研究资源也会集中到容易排名的问题上。久而久之，系统优化的目标可能不再是解决原问题，而是适应这套测试。

## 第四阶段：ImageNet 与排行榜文化

ImageNet 把大规模标注数据、年度竞赛和一个主要指标放在一起，明显推动了视觉模型发展。后来，GLUE 和 SuperGLUE 又用多任务套件推动语言理解。一个清晰数字确实能吸引人才和计算资源，但当这个数字决定论文、预算和采购时，团队也会更强烈地针对指标优化。

排行榜文化还带来了一个变化：benchmark 不再只是科研工具，也成了产品发布时的宣传材料。系统配置、提示词、工具和提交次数，常常被藏在一个模型名字后面；小数点后的差距被广泛传播，任务质量和结果不确定性却只留在附录里。

## 第五阶段：大模型的多任务、多指标与动态化

MMLU、BIG-bench、HELM 等项目把知识、推理、应用场景和多项指标放进统一框架。后来，公开题逐渐进入训练语料，选择题也接近满分。社区于是开始使用专家原创题、难以搜索的题、隐藏题和不断更新的题集。动态 benchmark 能减少直接背题，并持续发现新问题，但不同版本之间会更难比较，外部也更难完整审计。

中国的 C-Eval、CMMLU、OpenCompass 等项目补上了中文考试、中文知识和模型接入。但它们也说明，多语言评测绝不是把英文题翻译一下。语言、文化、制度、常用软件和业务习惯，都会改变任务本身。

## 第六阶段：Agent 把“答案”改成“行动”

WebArena、OSWorld、SWE-bench、τ-bench、TheAgentCompany 等项目把模型放进了会变化的环境。被测对象要浏览页面、调用工具、修改文件和数据库、处理失败，还要自己判断什么时候停止。这时，最后输出的一段文字已经不能代表结果：Agent 可能说“完成了”，环境里却什么都没变；它也可能把环境改对了，却走了一条危险路径。

因此，现代 Agent eval 开始加入环境重置、执行式 grader（直接运行并检查结果的评分器）、操作轨迹、工具预算、基础设施错误分类和连续可靠性。Harness 也不再只是实验用的脚手架，而成了被测系统的一部分。

## 第七阶段：从静态题库走向持续资格

当 AI 真正进入工作流程，benchmark 就要和发布门槛、上线后的持续复查连起来。一套新的评测系统通常会同时保留四类题：长期不变的锚题、研发看不到的资格题、持续更新的前沿题，以及来自生产事故的回归题。旧题集退役并不代表项目失败，而是承认这把尺子已经太容易、被污染，或者不再代表实际部署。

历史沿革可以压缩成一条主线：

```text
行为可观察
→ 条件可比较
→ 多任务可概括
→ 环境状态可验证
→ 组件贡献可归因
→ 岗位责任可授权
```

越往右，任务越接近真实工作，但也越难控制、复现和完全公开。新方法并没有淘汰旧方法：静态题仍适合做便宜的基础诊断，交互环境适合验证系统能否正确行动，生产证据适合决定是否扩大权限。成熟的团队知道每一层证据该用在什么时候。

## 六次历史迁移留下的设计债

历史不是一条只会变好的直线。每解决一个旧问题，评测基础设施里通常又会多出一个新问题。

| 迁移 | 解决的问题 | 新的设计债 |
|---|---|---|
| 心理测量尺度 | 从有限行为推断不可见能力 | 单维模型可能压扁多维能力 |
| 图灵式行为协议 | 把哲学问题变成可观察比较 | 测试边界决定“什么能被看见” |
| Shared task | 统一数据、切分和指标 | 数据集被误当成完整任务 |
| Leaderboard | 让进步清晰可传播 | 优化目标替代真实目标 |
| 多任务/多指标 | 扩展覆盖与责任维度 | 聚合权重继续隐藏价值判断 |
| Agent 环境 | 验证行动与终态 | 环境、Harness 和预算难以控制 |

设计新 benchmark 时，不要假装这些历史问题与你无关。你需要主动说明借用了哪种方法，也说明它带来了什么风险。做排行榜，就要限制反复提交造成的过拟合；用动态题集，就要解决不同版本怎样比较；用仿真，就要说明它与现实有多大差距；用专家题，就要披露样本和评审条件。

## 一个历史项目的四种读法

以 ImageNet 为例，可以从四个角度读。工程角度看数据规模、年度竞赛和模型进步；测量角度问标签和类别能不能代表视觉理解；制度角度看单一指标怎样集中研究资源；治理角度则关注数据来源、许可、偏差，以及项目饱和后怎样退出中心位置。同一个 benchmark，既是数据集，也是测量工具、竞赛规则和协调整个社区的制度。

今天看 SWE-bench、GDPval 或 SkillsBench，也应该保留这四个角度。只看技术题目，会漏掉提交规则和 Harness；只看社会争议，又会忽略执行式 verifier（验证器）带来的真实进步。把这些层面放在一起，才能理解一个 benchmark 到底在做什么。

## 历史如何帮助预测新争议

如果一个新榜单很快被采购或投资人采用，就可以预料到针对榜单优化、只提交优势项目，以及过度宣传小数点差异。如果一个动态题集宣称解决了污染，就要马上追问怎样复现、怎样跨时间比较。如果一个 Agent 环境宣称更真实，也要追问环境怎样维护、不同工具是否公平、人类基线怎样设置。

历史不能提前告诉我们哪道题有错，但能提醒我们优先检查哪些地方。

## 双案例镜头

云舟零售可以用公开中文知识集筛掉明显不合格的模型，但订单履约仍需要有状态沙箱。星桥硬件可以用代码和多模态题诊断基础能力，但研发放行必须检查真实工件间的追踪关系。历史告诉两家公司：不要要求底层诊断题承担岗位资格的责任。

## 练习：画出你的评测谱系

选一个现有 benchmark，标注它继承了哪种传统：考试、shared task、软件测试、偏好比较、仿真或生产监控。然后写出它为了获得可比性牺牲了什么，以及增加哪一层证据才能支持你的目标决策。
