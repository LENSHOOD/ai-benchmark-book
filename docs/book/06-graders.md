# Grader、人类评审与 LLM Judge

> **本章问题**：谁来判断答案对不对，以及如何知道裁判没有系统性地判错？

Grader（评分器）负责把系统行为转换成评测结果。它可以是精确答案匹配、单元测试、数据库断言、领域算法、规则、人工 rubric（评分标准），或者 LLM judge（用大模型做裁判）。Grader 不是 benchmark 旁边的一段脚本，而是测量系统的一部分：它决定我们看见哪些行为，也决定哪些错误会被漏掉。

Strict、diagnostic 与 veto 如何连接前后章节，见[框架总览](/appendix/framework-map)。

## 从可验证性最高的证据开始

一般先使用最容易复核的证据：

1. 环境终态和不可变业务断言；
2. 领域算法、编译、仿真与单元测试；
3. 必要轨迹、权限和政策规则；
4. 行为锚定的专家 rubric；
5. 经人工校准的 LLM judge。

这不代表排在前面的永远更重要，只是它们更容易复核。开放式写作确实需要人或模型来判断，但“退款有没有发生两次”“安全测试证据是否缺失”“代码是否通过回归”，不应该交给语言模型凭感觉决定。

## Strict success、诊断分与 Veto

业务评测最好同时给出三类结果。

**Strict success（严格成功）**要求所有关键终态都正确，没有发生禁止状态，需要升级时也确实升级。它用于资格门禁。

**诊断分**把目标拆成多个子项，告诉研发做对了哪些、错在什么地方。它用于修复问题，不能把“完成了一半”包装成业务价值。

**Veto（否决项）**代表严重到不能被平均分抵消的行为，例如越权付款、数据泄露、未经批准的安全放行或绕过联锁。只要触发，任务就失败，并单独进入风险报告。

过程分适合检查必须步骤、禁用工具、证据链、重复调用、恢复和升级。但不要要求系统完全复制唯一的示范轨迹。强系统可能找到更短、更安全的新路径；遇到这种情况，应该人工复核并更新任务规范，而不是直接判错。

## 人工评审不是无误差金标准

专家也会受到信息量、时间、呈现顺序和组织激励影响。人工评估要事先规定评审者资格、培训、允许查什么工具、时间限制、是否盲评、重复标注和分歧仲裁。人类基线还要说明到底是普通用户、领域专家，还是在真实工具和时间限制下工作的熟练员工。

至少要抽取一批重叠样本，估计评审者的一致程度。比一个总体一致率更有用的是看分歧集中在哪里：政策冲突、开放式建议，还是临界门禁？如果专家自己都无法稳定判断，系统分数就不应该报得像精确到小数点后一位一样。

## LLM-as-a-Judge 的位置

LLM judge 适合扩大开放任务的评估规模、解释 rubric 和生成诊断，但它可能受答案位置、篇幅、文风、同源偏好和自身推理能力影响。候选输出还可能反过来对 judge 进行提示注入。因此，候选内容、裁判指令和参考材料必须分开隔离。

最低限度的校准流程是：先建立一批专家 gold（人工确认的参考样本）；隐藏候选身份并随机顺序；交换 A/B 位置再测一次；比较多个 judge 或不同模型族；计算分类指标和各维度混淆矩阵；对低置信、严重分歧和 veto 案例人工仲裁；固定 judge 版本和 Prompt。模型或 Prompt 更新后，要重新校准。

不能只看 judge 和人类平均分的相关性。如果它在发布门槛附近经常翻转，或者把危险输出判成通过，即使总体相关很高，也不能用。门槛附近的条件错误率，比总体相关性更接近真实决策风险。

## Grader 也要接受单元测试

每条断言至少要用四类候选来测试：合理正解、替代正解、接近正确但仍有错的答案，以及危险捷径。如果替代正解被拒绝，说明 grader 太窄；如果近错解被接受，说明 grader 太宽；如果危险捷径被接受，说明安全门禁失效。

Grader Card（评分器说明卡）应记录：目标构念、输入、规则、权重、veto、依赖、版本、已知偏差、人工校准、覆盖测试和申诉流程。任何修改都可能改变历史分数，所以必须版本化。

## 一个 Judge 校准工作坊

假设团队要评价 300 份开放式根因分析。先让两位硬件专家独立标注 60 份，维度包括证据是否适用、因果论证、替代解释和验证计划；有分歧时由第三人仲裁。拿其中 40 份设计 Judge Prompt，留下 20 份做盲测。候选身份和顺序都随机，Judge 看不到最终门禁标签，只能看到工件和 rubric。

第一轮不要只算平均相关。先为每个维度建立混淆矩阵，重点检查两类案例：“证据缺失但文风专业”的近错解，以及“结论保守但证据充分”的替代正解。交换顺序再测，比较同源和异源 Judge。如果严重错误集中在“建议放行”这一维，就把它交回确定性规则或专家判断，不要继续微调一个总分 Prompt。

校准结果要保存 gold 样本、Prompt、模型快照、温度、输出 schema、阈值、分歧规则和已知失败。Judge 更新后，要在固定 gold 上做回归测试，不能默认新模型就更会评分。

## Grader 的三种漂移

**代码漂移**来自规则和测试的修改；**数据漂移**来自环境或政策变化；**语义漂移**来自团队改变了对“好”的定义。三种漂移都会改变历史结果。变更记录要写明哪些旧运行可以重新评分，哪些必须重新执行。

例如退款政策额度改变，旧 trace 可以用新规则重评分，但如果候选当时没有看到新政策，重评分不能代表新部署能力；需要在新环境重跑。区分重评分和重执行，避免时间穿越。

## 申诉是发现新合理路径的传感器

当候选找到了 grader 没覆盖、但业务上合理的路径，申诉不是额外负担，而是发现问题的传感器。评审者要判断它属于替代正解、任务歧义，还是危险投机。替代正解应加入 grader 测试并回溯重评分；任务歧义要修订规范；危险投机要加入负断言。允许申诉，并公开修订影响的 benchmark，通常比拒绝所有例外的评测更可信。

## 不确定输出怎样进门禁

Grader 可以输出 `pass`、`fail`、`veto`、`needs_review`，不必把所有 case 硬切成通过或失败。报告要写清 `needs_review` 占多少、严重程度如何、花了多少人工分钟。系统不能靠把大量任务转给人工来伪装质量。资格规则也要提前说明：人工复核怎样计入分母、由谁仲裁，以及什么时候算证据不足。

## 双案例镜头

云舟零售首先读取订单、库存和资金终态；模型 judge 只评价客户解释是否清晰且不误导。星桥硬件首先检查需求追踪、测试证据、器件约束和审批；专家 rubric 评价根因论证与验证计划，LLM judge 只在低风险诊断维度辅助。

## 练习：攻击你的 Grader

为一个任务写出五个候选：完全正确、表面漂亮但未执行、结果正确但路径不同、部分完成、危险捷径。运行或人工检查 grader 是否给出预期结果。每发现一个错误，先修 grader 测试，再修改规则。
