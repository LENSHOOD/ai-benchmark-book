# 为什么评测决定 AI 能走多远

> **本章问题**：如果模型演示看起来已经很好，为什么还要投入时间建设评测？

一家团队给新模型接上搜索、数据库和邮件工具，演示时只用一句话便完成了原本半小时的工作。会议室里的反应通常不是“测到了什么构念”，而是“什么时候上线”。几周后，团队才发现它在库存不足时重复建单、遇到政策冲突时选择更像答案的旧规则，并把“已经为您处理”写进了邮件，尽管数据库写入失败。

这些问题不是模型完全没有能力，而是团队从未把“完成”写成可执行标准。没有 benchmark，演示中的成功会成为事实标准；没有持续 eval，用户反馈会成为唯一传感器；没有发布门禁，每次模型、Prompt、Harness 或 Skill 更新都像更换关键零件却不做验收。

## Eval 是反馈系统，不是一次考试

Eval 比 benchmark 更宽。单元测试、离线资格评测、A/B 实验、生产监控、红队、安全审计和人工复核都属于 eval。Benchmark 通常是一套标准化任务、协议和指标，用于在相对一致条件下比较。Leaderboard 只是将部分结果排序展示。

三者混在一起时，团队会犯三个错误。第一，把公共题集的高分当作产品可靠性；第二，把一次 A/B 的用户偏好当作业务正确性；第三，把排行榜的名次当作模型的永久属性。实际上，任何分数都是某个版本化系统在某种测量政策下的一组观测。

可以把现代 AI 系统的**被测单位（system under test, SUT）**写成：

```text
Model × Harness × Skill × Tool/Environment access
```

模型决定生成与推理能力；Harness 决定上下文、工具、恢复、验证和终止；Skill 注入特定流程与知识；工具与环境访问决定系统能看到和改变的世界。Grader、预算、协议和评测政策属于**观测条件**：它们影响分数，却不应被误写成系统自身能力。只报告模型名，仍然等于省略了大半实验条件；把 grader 混入 SUT，则会让“改尺子”和“改系统”无法区分。第 3 章给出完整的[八层测量系统](./03-language#八层测量系统)。

## Benchmark 实际定义了产品

指标不只是观察产品，也会塑造产品。如果代码 Agent 只按补丁能否通过已有测试打分，团队会优化“通过测试”，而不一定优化可维护性、性能或安全。如果客服 Agent 只按对话满意度打分，它可能学会更快承诺，而不是更正确地处理订单。Goodhart 风险并不意味着取消指标，而是要求多层证据互相制衡。

一个有效 benchmark 至少支持四类反馈：

1. **研发反馈**：哪里失败，哪项修改有效；
2. **选型反馈**：在可比预算下哪个系统更适合目标任务；
3. **发布反馈**：风险、可靠性和成本是否达到门槛；
4. **治理反馈**：系统可以承担什么责任，何时需要复证或降权。

这四种用途不能共享同一套最优题集。研发集要稳定、便宜、对已知失败敏感；选型集要公平控制条件；资格集要接近真实任务且对研发隐藏；生产监控要接受分布变化和人的介入。最成熟的体系不是寻找“万能 benchmark”，而是让不同证据层各司其职。

## 两条案例线从同一个错误开始

在虚构企业**云舟零售**，一个履约助手根据客户等级、库存和承运事件提出处理方案。早期团队只评邮件是否通顺，结果系统能写出漂亮说明，却可能没有预留库存或触发退款。于是 benchmark 的真值必须落在订单、库存、资金和升级队列的状态上。

在虚构企业**星桥硬件**，研发助手读取需求、BOM、测试日志和缺陷，建议工程变更。早期团队只评分析报告是否专业，结果系统可能建议一个规格相近但温度等级不符的替代器件，或在安全测试缺证据时建议通过 DVT 门禁。这里的真值落在需求追踪、证据完整、审批和阶段状态上。

两条案例表面差异很大，但都揭示同一原则：自然语言产物只是界面，环境状态和责任边界才是业务结果。

## 建设评测的真实回报

评测的回报不只来自“选对模型”。它迫使产品、工程、业务和风险团队回答同一个问题：什么叫完成，什么绝不能发生，失败后如何恢复。当这些定义被写成任务和 grader，它们就从口头经验变成可测试契约。

长期看，benchmark 还会形成组织记忆。一次错退款、一次错误放行、一次政策冲突，不再只是复盘文档，而会成为回归任务。系统扩大权限，不靠更震撼的演示，而靠在新风险集上取得足够证据。AI-native 组织的差异，最终可能不在于谁先接入新模型，而在于谁能更快把生产经验转化成不会轻易说谎的反馈系统。

## 从零到一的 Eval Flywheel

初创团队不需要第一天建设大型平台。一个有效飞轮可以从十条失败开始。第一周，团队把最常见的成功和最担心的失败各写五条，明确初始状态、目标状态和禁止状态；第二周，用最简单的规则或人工检查跑当前系统，保存逐题输出；第三周，按失败原因修改 Prompt、Harness 或 Skill，并只在开发集迭代；第四周，把未参与开发的新题作为小型资格集，在固定预算下重新运行。

上线后，用户反馈不应只是一枚“赞/踩”。反馈需要关联任务、系统版本、真实终态、人工改动和失败严重度。每周从人工大改、错误自主和异常成本中选择少量新 case，先重建可复现 episode，再加入隐藏回归。这样，eval 不是季度专项，而是产品开发的反馈回路。

飞轮的关键是**每次运行都能改变下一项行动**。如果某项指标连续三个月没人查看，或查看后也不会修改设计、权限或预算，它很可能不值得维护。反之，即使只有二十条题，只要能稳定捕获重要失败、指导修复并阻断危险发布，也比一套漂亮但无人响应的千题面板更有价值。

### 五个成熟度台阶

| 台阶 | 团队行为 | 尚不能声称 |
|---|---|---|
| 示例驱动 | 保存代表输入输出，人工回看 | 稳定能力或泛化 |
| 回归驱动 | 已知失败自动复测 | 对未知任务有效 |
| 资格驱动 | 隐藏集、协议和门禁固定 | 生产分布持续成立 |
| 生产驱动 | 监控、事故回归、灰度和回滚 | 新岗位可自动授权 |
| 治理驱动 | 能力执照、复证和退役 | 永久无风险 |

团队应知道自己位于哪个台阶。把示例驱动包装成资格驱动，是很多 AI 产品最早的评测债务。

## 三个反直觉决策

第一，分数下降有时是进步。grader 修复了宽松断言、风险集加入真实事故后，分数会下降，但测量更诚实。第二，模型升级有时应缩权。更强模型可能提高普通成功，同时更自信地越过审批。第三，更多自动化不必然创造更多价值。若系统把复杂 case 更晚、更差地交给人，表面自治率提高，端到端周期却变长。

## 实践检查单

- 这次评测最终要支持研发、选型、发布还是授权决策？
- 被测对象是否写到了 Model 之外的 Harness、Skill、环境和预算？
- 分数对应真实完成、代理信号还是用户偏好？
- 严重失败能否被平均成功抵消？
- 生产中的新失败如何进入回归？

## 练习：写一页 Eval Purpose

选择你正在做的一个 AI 功能，用一页纸回答：决策者是谁；决策是什么；错误发布和错误拒绝各有什么代价；结果至少需要哪三类证据；哪些结论即使分数很高也不能推出。不要先列题目。
