# 为什么评测决定 AI 能走多远

> **本章问题**：如果模型演示看起来已经很好，为什么还要投入时间建设评测？

一家团队给新模型接上搜索、数据库和邮件工具。演示时，用户只说一句话，系统就完成了过去需要半小时的工作。会议室里最常听到的问题不是“我们到底测到了什么”，而是“什么时候上线”。

几周后，问题出现了：库存不够时，系统重复建单；两条政策冲突时，它选了措辞更像答案、但已经过期的那一条；数据库明明写入失败，它却在邮件里说“已经为您处理”。

问题不一定是模型太弱，更可能是团队从未说清楚什么才算“完成”。没有 benchmark（标准化评测集），一次漂亮的演示就容易被当成稳定能力；没有持续 eval（评估），用户投诉就成了唯一的报警器；没有发布门槛，每次更换模型、Prompt、Harness 或 Skill，都像换了关键零件却不验收。

## Eval 是反馈系统，不是一次考试

Eval 的范围比 benchmark 更大。单元测试、离线资格评测、A/B 实验、生产监控、红队测试、安全审计和人工复核，都属于 eval。Benchmark 通常指一套标准化的任务、运行规则和指标，用来在相对一致的条件下比较系统。Leaderboard（排行榜）只是挑出部分结果排个名。

把三者混在一起，会带来三个常见误判：把公共题集高分当成产品可靠；把一次 A/B 实验中的用户偏好当成业务正确；把榜单名次当成模型不会变化的属性。其实，任何分数都只说明：某个具体版本的系统，在一套具体评测规则下，表现如何。

可以把现代 AI 系统的**被测单位（system under test, SUT）**写成：

```text
Model × Harness × Skill × Tool/Environment access
```

模型决定系统能怎样生成和推理；Harness（运行框架）负责组织上下文、调用工具、处理失败、检查结果和决定何时结束；Skill（技能包）提供特定流程和知识；工具及环境权限决定系统能看到什么、能改动什么。Grader（评分器）、预算、运行协议和评测政策属于**观测条件**：它们会影响分数，但不是系统能力本身。

所以，只报告模型名，等于漏掉了大半实验条件。反过来，如果把 grader 也算进被测系统，我们就分不清究竟是“系统变好了”，还是“评分尺换了”。第 3 章会完整介绍[八层测量系统](./03-language#八层测量系统)。

## Benchmark 实际定义了产品

指标不只是在观察产品，它也会把产品引向某个方向。如果代码 Agent 只看补丁能不能通过现有测试，团队最终优化的可能只是“过测试”，而不是可维护性、性能或安全。如果客服 Agent 只看满意度，它可能学会更快答应客户，却没有把订单处理正确。

这就是 Goodhart 风险：当一个指标成了目标，人们就会设法优化指标，指标也就越来越不能代表原本的目标。解决办法不是不用指标，而是让不同证据互相校验。

一个有效 benchmark 至少支持四类反馈：

1. **研发反馈**：哪里失败，哪项修改有效；
2. **选型反馈**：在可比预算下哪个系统更适合目标任务；
3. **发布反馈**：风险、可靠性和成本是否达到门槛；
4. **治理反馈**：系统可以承担什么责任，何时需要复证或降权。

这四种用途，不能指望同一套题都做得最好。研发集要稳定、便宜，能迅速发现已知问题；选型集要保证不同候选在相同条件下运行；资格集要贴近真实任务，而且不能提前向研发人员泄题；生产监控则要面对任务分布变化，也要记录人工介入。成熟的做法不是寻找一套“万能 benchmark”，而是让每层证据解决自己的问题。

## 两条案例线从同一个错误开始

在虚构企业**云舟零售**，一个履约助手根据客户等级、库存和承运事件提出处理方案。早期团队只评邮件是否通顺，结果系统能写出漂亮说明，却可能没有预留库存或触发退款。于是 benchmark 的真值必须落在订单、库存、资金和升级队列的状态上。

在虚构企业**星桥硬件**，研发助手读取需求、BOM、测试日志和缺陷，建议工程变更。早期团队只评分析报告是否专业，结果系统可能建议一个规格相近但温度等级不符的替代器件，或在安全测试缺证据时建议通过 DVT 门禁。这里的真值落在需求追踪、证据完整、审批和阶段状态上。

两个案例看起来差别很大，但结论相同：自然语言只是系统给人看的界面。真正的业务结果，要看环境里发生了什么，以及系统有没有越过责任边界。

## 建设评测的真实回报

评测的价值不只在于“选对模型”。它会迫使产品、工程、业务和风险团队一起说清楚：怎样才算完成，哪些事情绝不能发生，失败后应该怎样恢复。把这些答案写进任务和 grader 后，原本只存在于员工经验里的标准，就变成了可以反复检查的契约。

长期来看，benchmark 还会保存组织记忆。一次错误退款、一次错误放行、一次政策冲突，不会只停留在复盘文档里，而会变成以后每次发布都要重跑的回归任务。系统要扩大权限，靠的也不该是更震撼的演示，而是它在新风险任务上积累了足够证据。AI-native 组织之间真正的差距，可能不在于谁先接入新模型，而在于谁能更快把生产经验变成可靠的反馈系统。

## 从零到一的 Eval Flywheel

初创团队第一天不需要建设大型评测平台。先从十条案例开始就够了。第一周，分别写下五个最常见的成功案例和五个最担心的失败案例，并说明初始状态、目标状态和禁止状态。第二周，用简单规则或人工检查跑一遍当前系统，保存每道题的输出。第三周，根据失败原因修改 Prompt、Harness 或 Skill，只在开发集上迭代。第四周，再拿一批没有参与开发的新题做小型资格集，并固定预算重新运行。

上线后，也不要只记录用户点了“赞”还是“踩”。反馈要能关联到具体任务、系统版本、真实终态、人工改了什么，以及问题有多严重。每周从人工大改、系统错误自主处理和成本异常里选少量新案例，先把它们重建成可重复运行的一次任务过程（episode），再加入隐藏回归集。这样，eval 才会成为产品每天都在用的反馈回路，而不是每季度做一次的专项。

这个飞轮能不能转起来，关键看**每次运行是否会改变下一步行动**。如果一个指标连续三个月没人看，或者看了也不会影响设计、权限和预算，它多半不值得继续维护。反过来，即使只有二十道题，只要它们能稳定抓住重要错误、帮助团队修复，并阻止危险版本上线，就比一个漂亮却没人响应的千题面板更有价值。

### 五个成熟度台阶

| 台阶 | 团队行为 | 尚不能声称 |
|---|---|---|
| 示例驱动 | 保存代表输入输出，人工回看 | 稳定能力或泛化 |
| 回归驱动 | 已知失败自动复测 | 对未知任务有效 |
| 资格驱动 | 隐藏集、协议和门禁固定 | 生产分布持续成立 |
| 生产驱动 | 监控、事故回归、灰度和回滚 | 新岗位可自动授权 |
| 治理驱动 | 能力执照、复证和退役 | 永久无风险 |

团队要清楚自己现在在哪个台阶。只有几个演示案例，却对外说已经通过正式资格评测，是很多 AI 产品最早欠下的评测债。

## 三个反直觉决策

第一，分数下降有时反而是进步。比如团队修复了过于宽松的评分规则，或者把真实事故加入风险集，分数会下降，但结果更诚实。第二，模型升级后有时应该先缩小权限。更强的模型可能提高普通任务成功率，也可能更自信地绕过审批。第三，自动化更多不等于价值更大。如果系统只是把复杂案例更晚、更糟地交给人，表面上的自主率提高了，端到端处理时间反而会变长。

## 实践检查单

- 这次评测最终要支持研发、选型、发布还是授权决策？
- 被测对象是否写到了 Model 之外的 Harness、Skill、环境和预算？
- 分数对应真实完成、代理信号还是用户偏好？
- 严重失败能否被平均成功抵消？
- 生产中的新失败如何进入回归？

## 练习：写一页 Eval Purpose

选择你正在做的一个 AI 功能，用一页纸回答：决策者是谁；决策是什么；错误发布和错误拒绝各有什么代价；结果至少需要哪三类证据；哪些结论即使分数很高也不能推出。不要先列题目。
