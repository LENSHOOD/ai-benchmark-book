# 评测评测本身，以及未来

> **本章问题**：怎样判断一套 benchmark 值得信任；未来评测会变成什么？

设计者经常严格评模型，却宽松对待题集。项目、答案、环境和 grader 可能错误；样本可能偏；协议可能混杂；指标可能被优化到失真。因此最后一项能力是 benchmark-the-benchmark：把评测自身当作需要测试、版本化和退役的系统。

## 十二维审查框架

::: warning 实践建议 · 本书审计框架
下面十二维是作者综合本书设计原则形成的审查清单，不是外部认证标准，也不应压成单一质量分。它在全书方法链中的位置见[框架总览](/appendix/framework-map)。
:::

1. **用途**：支持哪个决策，禁止哪些外推；
2. **构念**：边界和相邻能力是否明确；
3. **内容**：任务宇宙、频率、风险与群体是否覆盖；
4. **项目质量**：可解、清晰、多解与难度是否审计；
5. **协议控制**：模型、Harness、Skill、预算和工具是否披露；
6. **环境**：能否重置、复现、区分环境故障；
7. **Grader**：是否验证正解、近错和危险捷径；
8. **统计**：逐题、多 trial、区间和效应量是否匹配数据；
9. **基线**：人类与系统基线条件是否可比；
10. **污染与 Goodhart**：接触、切分、提交和优化压力如何管理；
11. **治理**：版本、修订、申诉、重评分与退役；
12. **可用性**：成本、代码、许可证和文档是否允许目标用户复现。

不要把十二维压成一个质量总分。一套适合快速研发的廉价 benchmark 可能不适合资格；私有资格集生态效度高，却无法公开复现。审查的目标是说明“适用于什么、不适用于什么、证据有多强”。

## 一次 Benchmark 审计工作坊

让设计者、目标用户、独立领域专家和未参与开发的工程师各自回答十二维问题，先独立后讨论。为每个维度附证据位置，不能只写“是”。例如“环境可复现”的证据应是重置测试、版本清单和失败日志；“grader 有效”的证据应是正解、近错、危险捷径与专家一致性结果。

随后选择三个主要决策结论做反向追踪：某系统可以上线、某 Skill 有增益、某风险可接受。逐层回到统计、trial、grader、环境状态和原始任务。如果链条中出现无法定位的聚合、人工改表或缺失版本，结论强度必须下调。

最后进行交换复现：另一位工程师在不询问作者的情况下，用文档重跑一小部分并解释结果。不能复现不一定说明算法错误，却说明 benchmark 还不是可移交的测量产品。

## 反证登记

对每个主要结论主动维护竞争性解释。例如成绩提高可能来自 grader 变宽、任务变容易、预算增加、环境稳定、污染或提交选择；Skill 平均增益可能掩盖关键负增益；人类偏好提升可能来自自动化偏见。

反证不是削弱研究，而是防止结论超出证据。最可信报告会公开已知问题、负结果、缺失运行和修订影响。

一个简单的反证登记包含：结论；竞争解释；如果解释成立应观察到什么；目前有哪些证据；下一项最便宜的区分实验；owner 与状态。例如“Workflow Harness 提升成功率”的竞争解释可能是它给了更多 token。预算匹配实验若消除增益，就不能继续把效果归因于工作流结构。

## 未来一：从静态题库到活的能力地图

::: info 未来推测
以下六个方向是基于当前项目演化与企业实践的趋势判断，不是对行业时间表或必然结果的事实陈述。每一项都需要持续用反例和版本化证据复核。
:::

未来 suite 会同时保留稳定锚题和滚动新题，用尺度等值连接版本。Leaderboard 的单一总名次下降，能力切片、难度、区间、任务级证据和状态标签上升。动态评测不仅防污染，也能发现旧构念遗漏的新行为。

## 未来二：从模型分数到系统因果归因

研究单位会从模型名转向版本化 Model × Harness × Skill × Environment。随着交叉数据积累，混合效应、因果消融和预算匹配成为常规披露。厂商若不披露 Harness、工具与推理预算，其“模型成绩”越来越难被视为可比较证据。

## 未来三：评测器组合与 Judge 治理

LLM judge 不会消失，但会从万能裁判退回组合角色：状态 verifier 管终态，领域算法管结构化质量，模型 judge 管开放维度，专家管校准与争议。Judge 自身拥有 benchmark、版本、偏差卡、提示注入测试和持续监控。

## 未来四：数字孪生与影子生产融合

企业 Agent benchmark 会与流程挖掘、可观测性和数字孪生合并。生产 trace 更新任务分布，conformance checking 识别政策偏离，事故自动形成候选回归，资格与 canary 形成闭环。最有价值的 benchmark 往往不会公开，因为它沉淀了企业的流程和失败知识。

## 未来五：从分数到能力执照

数字员工会形成可审计的职责对象：任务范围、工具、数据域、权限、证据、到期和复证。自主程度不再是模型固有等级，而由能力证据、业务风险、人的责任和恢复机制共同决定。

## 未来六：从岗位替代到组织重构

当数字员工跨越流程节点，价值不能只按节省人工小时衡量。更重要的是端到端周期、等待与交接、一次成功、例外闭环、决策一致、可审计、客户价值和流程是否被重构。Benchmark 最终成为业务契约：规定系统承担什么，人在哪些地方保留判断与最终责任。

## 尚未解决的研究议程

第一，真实长程任务昂贵而稀疏，怎样在不损失构念的前提下用代理任务预测生产表现；第二，开放环境不断变化，怎样同时保持可复现与生态效度；第三，模型、Harness 和 Skill 共同学习后，如何在强交互中稳定归因；第四，怎样测量正确升级、团队协作和跨周记忆，而不把任务简化成单 episode；第五，如何估计罕见严重风险而不宣称“样本中零事故”等于安全。

企业层还有更难的问题：谁拥有流程 trace 和从事故生成的题目；员工如何申诉数字化岗位标准；能力执照怎样跨部门或供应商互认；benchmark 会不会反过来固化一个本应被重构的坏流程。这些不只是统计问题，也是组织设计与治理问题。

## 接下来十二个月的实践路线

第一个月选择窄决策，写 Charter、人工基线和十个锚题；第二至三个月扩展任务宇宙、状态 grader 和可重置环境；第四个月运行组件矩阵并校准专家判断；第五至六个月建立隐藏资格与风险集；随后进入只读、影子和小流量自治；每次变化用事故与人工修改更新回归。不要等“完美 benchmark”才开始，但每一步都要清楚当前证据允许什么决定。

成熟度的标志不是题目最多，而是团队能迅速回答：本次分数为何变化；哪类任务受影响；能否归因；风险是否越过红线；应该扩大、维持还是收缩权限；下一项最有信息量的实验是什么。

## 最后的原则

基础模型 benchmark、Agent benchmark 和企业资格评测不能互相替代。前者提供可复现诊断，中者证明行动系统能力，后者决定责任授权。连接三层，需要测量学的构念意识、软件测试的执行验证、实验科学的控制、可靠性工程的尾部风险，以及组织对责任与价值的定义。

真正成熟的评测不会承诺永不出错。它会明确不知道什么，保留反证入口，在环境变化时重新验证，并把每次失败转化为更好的测量系统。

## 毕业项目

从两条案例中选择一条或使用自己的场景，提交：Charter、构念图、任务宇宙、开发/资格/风险切分、数字孪生、grader 测试、全交叉预注册、逐题结果、发布门禁、能力执照和生产复证计划。另一位读者应能依据材料复现实验并指出适用边界。

完成这些工件，你不再只是 benchmark 的消费者，而开始成为测量系统的设计者。

## 毕业答辩检查表

- 能否用一句话说明支持的决策，而不是只说“测能力”；
- 是否展示至少一项构念外的高分捷径，并由 grader 拒绝；
- 是否有频率、风险、近错、故障和正确升级任务；
- 是否保留逐题、逐 trial、组件版本与环境状态；
- 是否用人类/现状基线和不确定区间解释差异；
- 是否存在不会被平均分抵消的 veto；
- 是否把发布权限限定到证据覆盖的任务族；
- 是否能由第二个人复现、申诉、修订和退役。

如果其中任何一项回答不了，最好的下一步通常不是再跑一个更大的模型，而是补上测量链条中缺失的证据。
