# 谁来检查评测，以及下一步会发生什么

> **本章问题**：怎样判断一套 benchmark 值得信任；未来评测会变成什么？

团队常常严格检查模型，却默认题集没有问题。其实题目、答案、环境和评分器都可能错，样本也可能偏，指标还可能被“刷”到失去意义。所以最后一项能力是检查 benchmark 本身：它也要被测试、版本化，必要时还要退役。

## 十二维审查框架

::: warning 实践建议 · 本书审计框架
下面十二项是本书整理出的审查清单，不是外部认证标准，也不该再压成一个总分。它在全书方法链中的位置见[框架总览](/appendix/framework-map)。
:::

1. **用途**：支持哪个决策，禁止哪些外推；
2. **构念**：边界和相邻能力是否明确；
3. **内容**：任务宇宙、频率、风险与群体是否覆盖；
4. **项目质量**：可解、清晰、多解与难度是否审计；
5. **协议控制**：模型、Harness、Skill、预算和工具是否披露；
6. **环境**：能否重置、复现、区分环境故障；
7. **Grader**：是否验证正解、近错和危险捷径；
8. **统计**：逐题、多 trial、区间和效应量是否匹配数据；
9. **基线**：人类与系统基线条件是否可比；
10. **污染与 Goodhart**：接触、切分、提交和优化压力如何管理；
11. **治理**：版本、修订、申诉、重评分与退役；
12. **可用性**：成本、代码、许可证和文档是否允许目标用户复现。

不要把十二项再算成一个“质量总分”。便宜的 benchmark 可能很适合日常研发，却不够资格考试用；私有资格集更接近真实业务，却无法公开复现。审查要说清它能用于什么、不能用于什么、证据有多强。

## 一次 Benchmark 审计工作坊

请设计者、目标用户、独立领域专家和没参与开发的工程师分别回答十二个问题，先各自写，再一起讨论。每个答案都要指向证据，不能只写“是”。例如“环境可复现”要拿出重置测试、版本清单和失败日志；“评分器可信”要拿出正解、近错、危险捷径和专家一致性结果。

再挑三个最重要的结论，例如“系统可以上线”“Skill 有帮助”“风险可以接受”。从结论一路倒查到统计、trial、评分器、环境状态和原始任务。中间只要出现找不到来源的汇总、人工改表或缺失版本，就要降低结论强度。

最后进行交换复现：另一位工程师在不询问作者的情况下，用文档重跑一小部分并解释结果。不能复现不一定说明算法错误，却说明 benchmark 还不是可移交的测量产品。

## 反证登记

对每个主要结论主动维护竞争性解释。例如成绩提高可能来自 grader 变宽、任务变容易、预算增加、环境稳定、污染或提交选择；Skill 平均增益可能掩盖关键负增益；人类偏好提升可能来自自动化偏见。

反证不是削弱研究，而是防止结论超出证据。最可信报告会公开已知问题、负结果、缺失运行和修订影响。

一张简单的反证表写六件事：当前结论；另一种解释；如果另一种解释是真的，会看到什么；现在有什么证据；最便宜的验证实验；负责人和状态。例如“Workflow Harness 提高成功率”也可能只是因为它用了更多 token。把预算调成一样后，如果提升消失，就不能再说是工作流结构的功劳。

## 未来一：从静态题库到活的能力地图

::: info 未来推测
以下六个方向是基于当前项目演化与企业实践的趋势判断，不是对行业时间表或必然结果的事实陈述。每一项都需要持续用反例和版本化证据复核。
:::

未来的题集会同时保留一批长期不变的锚题，也不断加入新题。版本之间需要做等值连接，避免每次更新后数字完全不可比。单一排行榜名次会变得没那么重要，能力切片、难度、区间、逐题证据和状态标签会更重要。

## 未来二：从模型分数到系统因果归因

评测对象会从一个模型名，变成有版本的 Model × Harness × Skill × Environment。报告也会更常说明做了哪些消融、预算是否一样、不同组件怎样互相影响。如果不披露 Harness、工具和推理预算，“模型成绩”会越来越难比较。

## 未来三：评测器组合与 Judge 治理

LLM judge 不会消失，但不该继续当万能裁判。状态验证器检查终态，领域算法检查结构化质量，模型 judge 评价开放内容，专家负责校准和争议。Judge 自己也要有 benchmark、版本、偏差记录、提示注入测试和持续监控。

## 未来四：数字孪生与影子生产融合

企业 Agent benchmark 会越来越接近生产系统。生产 trace 会更新题目分布，流程检查会找出偏离政策的动作，事故会变成候选回归题，资格测试和小流量 canary 会连成一条链。最有价值的题集往往不会公开，因为里面装着企业最真实的流程和失败经验。

## 未来五：从分数到能力执照

数字员工会形成可审计的职责对象：任务范围、工具、数据域、权限、证据、到期和复证。自主程度不再是模型固有等级，而由能力证据、业务风险、人的责任和恢复机制共同决定。

## 未来六：从岗位替代到组织重构

当数字员工跨越流程节点，价值不能只按节省人工小时衡量。更重要的是端到端周期、等待与交接、一次成功、例外闭环、决策一致、可审计、客户价值和流程是否被重构。Benchmark 最终成为业务契约：规定系统承担什么，人在哪些地方保留判断与最终责任。

## 尚未解决的研究议程

仍有五个难题没有答案：真实长任务又贵又少，怎样用便宜任务预测生产表现；环境一直在变，怎样同时做到可复现和接近现实；模型、Harness 和 Skill 一起变化时，怎样分清谁起了作用；怎样测正确求助、团队协作和跨周记忆；怎样估计罕见严重风险，而不把“这次没出事故”误当成安全。

企业层还有更难的问题：谁拥有流程 trace 和从事故生成的题目；员工如何申诉数字化岗位标准；能力执照怎样跨部门或供应商互认；benchmark 会不会反过来固化一个本应被重构的坏流程。这些不只是统计问题，也是组织设计与治理问题。

## 接下来十二个月的实践路线

第一个月选一个窄决策，写 Charter、人工基线和十个锚题。第二到三个月扩充任务范围、状态评分器和可重置环境。第四个月跑组件矩阵并校准专家判断。第五到六个月建立隐藏资格集和风险集。之后再进入只读、影子和小流量自治。不要等“完美 benchmark”才开始，但每一步都要知道当前证据只允许做什么决定。

成熟度的标志不是题目最多，而是团队能迅速回答：本次分数为何变化；哪类任务受影响；能否归因；风险是否越过红线；应该扩大、维持还是收缩权限；下一项最有信息量的实验是什么。

## 最后的原则

基础模型 benchmark、Agent benchmark 和企业资格评测不能互相替代。第一层帮你诊断基础能力，第二层检查系统会不会行动，第三层决定它能承担什么责任。把三层连起来，需要明确“想测什么”、检查真实执行、控制实验条件、关注严重风险，也需要组织自己定义责任和价值。

真正成熟的评测不会承诺永不出错。它会明确不知道什么，保留反证入口，在环境变化时重新验证，并把每次失败转化为更好的测量系统。

## 毕业项目

从两条案例中选一条，或使用自己的场景。提交 Charter、能力定义图、任务范围、开发/资格/风险切分、模拟环境、评分器测试、实验计划、逐题结果、发布门禁、能力执照和生产复证计划。另一位读者应该能只看这些材料就重跑实验，并指出它的适用边界。

完成这些工件，你不再只是 benchmark 的消费者，而开始成为测量系统的设计者。

## 毕业答辩检查表

- 能否用一句话说明支持的决策，而不是只说“测能力”；
- 是否展示至少一项构念外的高分捷径，并由 grader 拒绝；
- 是否有频率、风险、近错、故障和正确升级任务；
- 是否保留逐题、逐 trial、组件版本与环境状态；
- 是否用人类/现状基线和不确定区间解释差异；
- 是否存在不会被平均分抵消的 veto；
- 是否把发布权限限定到证据覆盖的任务族；
- 是否能由第二个人复现、申诉、修订和退役。

如果其中任何一项回答不了，最好的下一步通常不是再跑一个更大的模型，而是补上测量链条中缺失的证据。
