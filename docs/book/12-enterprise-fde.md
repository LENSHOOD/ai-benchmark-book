# 企业 Benchmark 与 FDE 工作法

> **本章问题**：公开 benchmark 很多，为什么企业仍需要建设私有业务评测？

公开 benchmark 为模型和工程方法提供共同语言，但无法携带某家企业的私有 SOP、主数据、权限、客户承诺、异常、损失函数和组织责任。一个 Agent 在公开 CRM 环境成功，不代表它理解本公司的审批层级；一个中文模型考试高分，不代表它能正确处理渠道政策、票税或器件变更。

企业 benchmark 的本体是岗位契约：在什么触发、数据、工具、权限、政策和预算下，系统可以承担什么责任，什么必须升级，什么绝不能发生。

## 四个结构冲突

真实性与可公开性冲突：最有价值的合同、邮件、价格、库存和事故不能公开。稳定性与现实性冲突：生产系统持续变化，固定环境只能冻结一部分。自动评分与专业判断冲突：数据库状态可断言，商业与工程权衡仍需专家。外部可比性与内部相关性冲突：统一题库便于选型，却抹掉企业独有流程。

::: warning 实践建议 · 本书框架
本书建议用四层证据连接公开诊断与企业授权：公共诊断层、可共享合成孪生层、企业私有资格层和生产复证层。它是组织证据边界的设计框架，不是行业认证分级；与全书其他框架的关系见[框架总览](/appendix/framework-map)。越靠近生产越接近业务价值，也通常越昂贵、私密和动态。
:::

## FDE 的十阶段工作法

::: warning 实践建议 · 作者工作流
以下十阶段是把本书方法组织成 FDE 项目节奏的作者提案。企业可以合并或迭代执行，但不能跳过责任边界、独立 grader 和生产复证这些证据功能。
:::

### 1. 从价值假设选择窄岗位切片

不要以“做一个采购 Agent”开场。选择触发明确、输入可得、终态可验证、频率足够且风险可控的切片，例如“处理有替代库存的延期订单”或“审查 DVT 缺陷是否具备关闭证据”。记录人工基线、等待、返工、错误和损失。

### 2. 共同定义责任与红线

业务、研发、风险和系统团队一起写“完成”和“不能发生”。列出允许工具、数据域、金额/阶段权限、需审批动作、必须升级情形、可逆性与申诉。没有责任边界，自治率没有意义。

### 3. 发现真实流程而非只抄 SOP

结合跟岗、访谈、事件日志、审计、异常与事故。O*NET 类岗位模型可帮助分解任务、知识、技能与工具；流程挖掘发现实际路径、偏差和瓶颈。SOP 描述“应该怎样”，日志描述“实际怎样”，事故描述“哪里最危险”。

### 4. 版本化知识与证据

将政策、术语、主数据、例外、联系人、生效期和冲突优先级变成可版本化资产。知识库必须可回滚、可测试。每项规则需要来源与生效条件，避免把一次访谈意见变成永久真理。

### 5. 建立任务宇宙和双分布

频率集按生产分布估计价值；风险集按严重度、不可逆性、攻击面和失败模式抽样。任务来自专家原创、生产 trace、事故/风险分析和参数化合成。按实体和时间切分。

### 6. 搭建业务数字孪生

环境模拟必要的数据库、工具、权限、虚拟时钟和外部事件。所有写入可追踪与回滚；高风险动作先在沙箱。数字孪生不必复制整个企业，只需忠实承载目标构念和损失。

### 7. 构建评测器组合

用状态断言验证结果，用规则检查权限和政策，用领域算法验证结构化工件，用专家 rubric 判断开放质量，最后才是校准的 LLM judge。grader 先接受攻击测试，再评系统。

### 8. 运行基线、交叉实验和故障注入

先测熟练员工与现有流程，再运行 Model × Harness × Skill 条件。固定预算、按任务配对、多 trial。注入缺数据、权限不足、工具失败、政策冲突、并发和恶意输入。没有人类或现状基线，自动化收益缺少参照。

### 9. 分级授权而非一次上线

从只读建议、影子写入、低风险自主、高风险人批到岗位域内自治逐级放权。每一级明确任务范围、权限、成本、通过证据、到期日和回滚。更强模型只能提出扩权申请，不能自动获得更大权限。

### 10. 生产复证与事故回归

监测任务分布、正确完成、升级、人工大改、成本、共同故障和风险事件。把事故、人工大改和异常高成本 case 结构化成新回归。模型、Harness、Skill、政策、工具或数据域变化都可能触发复证。

## 数字员工评分卡

建议至少保留八个维度：业务结果；流程与政策；多次可靠性；自主与接管；人机协作；效率与经济性；风险与治理；学习与适应。质量维度可连续评分，严重风险使用 veto。

“正确且无需人工完成的任务占比”可以描述有效自主，但必须与正确升级、错误自主和人工分钟并列。高自治率可能只是少升级，高升级率也可能只是把困难推给人。

## FDE 的可复用资产

FDE 不应带走客户私有知识。跨项目可复用的是方法、协议、环境接口、grader 模式、任务 schema、失败分类、统计、门禁和治理模板。客户的合同、价格、主数据和事故保留在客户边界内。

长远看，FDE 的核心工作不是把模型接入系统，而是帮助组织把隐性责任变成可执行、可审计、可复证的能力标准。

## 业务工件图：避免把知识库误当成全部上下文

企业知识不是一个文档文件夹，而是一张有时效和责任的工件图。最少应区分六类节点：描述意图的政策与 SOP；描述对象的客户、商品、订单、BOM 等主数据；描述发生过什么的事件；描述当前事实的系统状态；描述谁能决定什么的权限与审批；描述结果是否成立的证据。边表示版本适用、引用、派生、审批、替代和冲突。

FDE 可以先画一个窄流程的“证据路径”：触发事件从哪里来，Agent 做每项判断需要哪份事实，动作写到哪里，谁批准，最终由哪个状态证明闭环。如果其中一项只能回答“大家都知道”，它就是需要显式化的隐性知识；如果两个系统都声称自己是真相源，就必须在 benchmark 之前解决优先级。

这也解释了为什么单纯提高 RAG 命中率往往不能证明数字员工胜任。检索到政策只是证据路径的一步；还需要确认政策版本适用、订单状态没有变化、当前角色有权限、动作真正落库、后续通知已经送达。每条路径都可以变成 Task Spec 的前置、必要证据、动作断言和终态断言。

## 从访谈到题目的取证工作坊

一次有效的流程访谈不问“标准流程是什么”，而请业务专家复盘三个最近案例：一个顺利完成、一个需要多次交接、一个险些或已经造成损失。对每个案例按时间线追问：当时看到了什么；为什么相信它；还考虑过哪些方案；哪项规则排除了其他方案；哪个动作不可逆；什么时候决定升级；最后怎样知道真的完成。

访谈后不要直接写题。先把陈述分成事实、规则、启发式、个人偏好和未知五类，并回到日志、制度或第二位专家处交叉核验。再将一个真实案例变形成题族：保持构念不变，替换实体和数值；改变一个关键约束制造近错；移除一项证据测试正确升级；注入工具部分失败测试恢复。这样获得的不是聊天题，而是一组能区分能力边界的对照实验。

## 30/60/90 天建设路线

::: warning 实践建议 · 示例节奏
下面的 30/60/90 天和“二十到五十个锚点任务”是便于团队启动的示例性节奏，不是来自跨企业研究的通用工期或行业标准。流程风险、数据准备和专家可用性不同，实际计划可能更短，也可能需要数个季度。
:::

前 30 天的目标是可判定，不是自动化。完成岗位切片、人工基线、责任红线、二十到五十个锚点任务和最小状态 grader。若团队仍无法就“完成”达成一致，应缩小流程，不要急着比较模型。

第 31—60 天建立最小数字孪生、频率/风险双集、grader 单元测试和 Model × Harness × Skill 基线。邀请未参与出题的专家盲审一批输出，检查 benchmark 是否奖励了业务真正认可的行为。此阶段最重要的交付是失败分类：模型知识不足、工具不可用、Skill 流程缺失、环境不忠实、题目错误，分别由不同 owner 修复。

第 61—90 天才进入影子与有限 canary。为每一级权限写证据门槛、停止条件和回滚演练；把人工修改、异常成本、错误自主和生产漂移接入回归流水线。九十天不是“数字员工毕业”的承诺，而是形成一条可以持续给出授权证据的生产线。

## 角色与职责

业务 owner 定义价值、损失与最终责任；领域专家提供案例、判定争议和复核内容效度；FDE 连接流程、数据、环境和实验；Agent 工程师实现 Harness 与 Skill；平台团队保证可重置工具和可观测性；风险/安全团队定义 veto 与权限；Eval owner 独立维护协议、隐藏集、版本和申诉。

出题者与被测系统开发者可以协作，但资格集保管和最终门禁最好有独立责任。专家意见不一致时，应记录分歧和升级路径，而不是由 FDE 私下选择一个更容易自动评分的答案。

## 经济性不是“调用成本越低越好”

企业价值至少包含：减少的等待和返工、避免的损失、增加的吞吐与服务价值，减去模型/工具成本、人工监督、环境维护、事故与机会成本。单位成功成本应以“无严重错误的完整闭环”为分母；把失败调用也计入分子。否则一个廉价但经常失败的系统会显得虚假高效。

还要防止局部最优。Agent 可能减少自己环节的人工分钟，却制造更多下游复核；缩短平均处理时间，却让长尾客户等待更久；提高自动关闭率，却增加重开。端到端周期、人工接管分钟、重开率和风险损失应与局部指标并列。

## 常见失败模式

- **从演示倒推构念**：先看到模型能做什么，再把容易成功的动作定义成岗位；
- **把 SOP 当真实分布**：只测理想路径，遗漏跨系统等待、例外与事故；
- **让同一位专家包办一切**：个人偏好被固化成 gold，争议没有申诉；
- **用一个总分汇报**：频率成功掩盖罕见严重错误；
- **把升级当失败**：迫使系统在证据不足时猜测；
- **先给生产权限再补测试**：事故成为发现构念边界的第一种方式；
- **项目结束即冻结**：政策、工具与数据变了，资格证据仍沿用旧版本。

这些失败看起来分别属于产品、数据、工程和治理，本质却相同：没有把“系统为什么可以承担这项责任”组织成可反驳的证据链。
