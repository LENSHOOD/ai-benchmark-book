# 企业 Benchmark 与 FDE 工作法

> **本章问题**：公开 benchmark 很多，为什么企业还要做自己的业务评测？

这一章把前面的 Model、Harness、Skill、环境和评分器合到一条企业落地流程里。它们之间的关系见[框架总览](/appendix/framework-map)。

公开 benchmark 能帮大家用同一把尺子比较模型和工程方法，但它不知道你公司的 SOP、主数据、权限、客户承诺、异常和损失。模型在公开 CRM 环境里做得好，不等于它知道你公司的审批顺序；中文考试分数高，也不等于它能正确处理你的渠道政策或器件变更。

企业 benchmark 真正要回答的是一份岗位契约：在什么输入、工具、权限、政策和预算下，系统可以自己承担什么责任；什么情况必须找人；什么事绝不能做。

## 四个结构冲突

最有价值的合同、价格、库存和事故不能公开，所以真实性和可分享性会冲突。生产系统一直在变，所以稳定复现和现实情况会冲突。数据库状态可以自动检查，但商业和工程取舍仍需要专家。统一题库便于选型，却可能漏掉企业自己的流程。

::: warning 实践建议 · 本书框架
本书建议用四层证据把公开诊断连接到企业授权：公共诊断、可共享的合成孪生、企业私有资格、生产复证。这是组织证据边界的设计框架，不是行业认证等级。越靠近生产，越接近业务价值，也越贵、越私密、越容易变化。
:::

## FDE 的十阶段工作法

::: warning 实践建议 · 作者工作流
下面十步是把方法落到 FDE 项目里的建议顺序。企业可以合并步骤，但不能省掉责任边界、独立评分器和生产复证。
:::

### 1. 从价值假设选择窄岗位切片

不要一开始就说“做一个采购 Agent”。先选一小段流程：触发清楚、输入拿得到、结果能检查、发生频率够高、风险又可控。例如处理有替代库存的延期订单，或审查 DVT 缺陷是否具备关闭证据。先记录人工花多少时间、等多久、返工多少和错一次会损失什么。

### 2. 共同定义责任与红线

业务、研发、风险和系统团队一起写清“完成”和“不能发生”。列出能用哪些工具、能看哪些数据、金额或阶段上限、哪些动作要审批、什么情况必须升级、动作能不能撤回。没有这条边界，自治率没有意义。

### 3. 发现真实流程而非只抄 SOP

跟岗、访谈、看事件日志、审计记录、异常和事故。SOP 说“应该怎么做”，日志说“实际怎么做”，事故说“哪里最危险”。O*NET 一类岗位模型可以帮你拆出任务、知识、技能和工具。流程挖掘能帮你找出偏离和瓶颈，但不能替专家做责任判断。

### 4. 版本化知识与证据

把政策、术语、主数据、例外、联系人、生效期和冲突优先级做成可回滚、可测试的资产。每条规则都写来源和适用条件，不要把一次访谈意见当成永久真理。

### 5. 建立任务宇宙和双分布

频率集按日常生产比例估计价值；风险集按严重度、不可逆性、攻击面和失败模式抽样。题目来自专家原创、生产 trace、事故分析和参数化合成。按实体和时间切分，防止同一案例的改写泄漏到资格集。

### 6. 搭建业务数字孪生

环境只需模拟和目标构念有关的数据库、工具、权限、虚拟时间和外部事件。所有写入都可追踪、可回滚，高风险动作先在沙箱里做。数字孪生不是复制整个企业，而是忠实承载你要测的责任和损失。

### 7. 构建评测器组合

状态断言检查结果，规则检查权限和政策，领域算法检查结构化工件，专家 rubric 检查开放质量，校准过的 LLM judge 只在合适的位置辅助。评分器本身也要先过正解、近错和危险捷径测试。

### 8. 运行基线、交叉实验和故障注入

先测熟练员工和现有流程，再跑 Model × Harness × Skill 条件。固定预算、按任务配对、多次运行。注入缺数据、权限不足、工具失败、政策冲突、并发和恶意输入。没有人工或现状基线，自动化收益没有参照。

### 9. 分级授权而非一次上线

从只读建议、影子写入、低风险自主、高风险人批，逐级走向岗位域内自治。每一级都写清任务范围、权限、成本、通过证据、到期日和回滚。更强模型只能申请扩权，不能自动获得扩权。

### 10. 生产复证与事故回归

监测任务分布、正确完成、升级、人工大改、成本、共同故障和风险事件。把事故、人工大改和异常高成本案例变成新回归。模型、Harness、Skill、政策、工具或数据范围变化，都可能触发重新验证。

## 数字员工评分卡

至少保留八个维度：业务结果；流程与政策；多次可靠性；自主与接管；人机协作；效率与经济性；风险与治理；学习与适应。普通质量可以连续打分，严重风险用 veto。

“正确且不用人工完成的任务占比”可以描述有效自主，但必须和正确升级、错误自主、人工分钟一起看。高自治率可能只是少求助，高升级率也可能只是把难题推给人。

## FDE 的可复用资产

跨项目可以复用方法、协议、环境接口、评分器模式、任务 schema、失败分类、统计、门禁和治理模板。客户的合同、价格、主数据和事故必须留在客户边界内。

FDE 的核心不是把模型接进系统，而是帮组织把隐性责任写成可执行、可审计、可复证的能力标准。

## 业务工件图：避免把知识库误当成全部上下文

企业知识不是一个文档文件夹，而是一张带时效和责任的工件图。至少区分六类东西：描述意图的政策和 SOP；描述对象的客户、商品、订单、BOM 等主数据；描述发生过什么的事件；描述当前事实的系统状态；描述谁能决定什么的权限和审批；描述结果是否成立的证据。

图里的连线也要有明确含义。例如：哪个版本适用于哪个对象，哪条结论引用了哪份材料，哪个状态由什么事件产生，谁批准了哪个动作，新工件替代了什么，以及两份材料在哪里冲突。没有这些关系，六类工件仍只是一堆文件。

先画一条窄流程的证据路径：触发事件从哪里来；每项判断需要哪份事实；动作写到哪里；谁批准；哪个状态证明闭环。如果只能说“大家都知道”，那就是需要显式化的隐性知识。如果两个系统都声称自己是真相源，先解决优先级，再开始 benchmark。

检索到政策只是其中一步。还要确认版本适用、订单没有变化、当前角色有权限、动作真的落库、后续通知已经送达。每一步都可以变成 Task Spec 的前置条件、必要证据、动作断言和终态断言。

## 从访谈到题目的取证工作坊

不要只问“标准流程是什么”。请业务专家复盘三个最近案例：一个顺利完成、一个交接很多、一个险些或已经造成损失。按时间线追问：看到了什么；为什么相信它；还考虑过什么；哪项规则排除了其他方案；哪个动作不可逆；什么时候决定升级；最后怎样知道完成。

访谈后先把陈述分成事实、规则、启发式、个人偏好和未知，再回到日志、制度或第二位专家处核验。然后把真实案例变成题族：替换实体和数值保持构念；改变一个约束制造近错；拿掉一项证据测试正确升级；注入工具失败测试恢复。

这段交付前的工作，也可以成为评测对象。过去常把完整政策、工具和题目交给业务 Agent，再问它能否执行。另一种考试是只给零散资料、可访谈的客户和已有接口，让开发 Agent 自己澄清需求、整理知识、实现业务 Agent，最后接受隐藏验收。

::: info 来源事实 · τ^τ-Bench
[τ^τ-Bench v1](https://arxiv.org/html/2609.04611v1) 于 2026 年 9 月 4 日提交，名称读作 hyper-tau-bench。它把上述构建过程放进受控环境：开发 Agent 可询问模拟客户、检查客户 API，并在时间与服务预算内交付另一个 Agent。最终用隐藏模拟用户检查数据库结果和沟通要求。

论文有 53 个公开构建任务、4 个领域，其中银行占 35 个；每个开发配置每任务只构建一次。客户和最终用户都是模拟的，专家参考方案还使用了作者掌握的真值。因此作者报告的成绩不能当成普通 FDE 的成功率，也不是生产项目认证。本书未复跑外部构建实验。
:::

沿用本书双案例，可以做两层验收。第一层检查是否找齐政策版本、澄清冲突、识别接口缺陷；第二层检查交付的 Agent 是否正确处理订单或研发工件。两层分别报告。不能因代码能运行，就忽略需求漏项；也不能因访谈做得好，就替最终产物免试。这是可扩展的出题方案，当前规则示例没有实现客户访谈与 Agent 自动构建。

## 30/60/90 天建设路线

::: warning 实践建议 · 示例节奏
下面的天数和“二十到五十个锚点任务”只是启动示例，不是行业标准。数据准备和专家时间不同，实际可能更快，也可能需要几个季度。
:::

前 30 天只追求“能判定”，不是自动化。完成岗位切片、人工基线、责任红线、二十到五十个锚点任务和最小状态评分器。如果团队还无法就“完成”达成一致，就缩小流程。

第 31—60 天建立最小数字孪生、频率/风险双集、评分器单元测试和 Model × Harness × Skill 基线。邀请没参与出题的专家盲审，确认 benchmark 奖励的是业务认可的行为。

这一阶段还要把失败分清楚：是模型不知道，工具不可用，Skill 漏了流程，模拟环境不准确，还是题目本身有错。不同问题要交给不同负责人修，不能都归成“模型失败”。

第 61—90 天才进入影子与小流量 canary。为每一级权限写证据门槛、停止条件和回滚演练，把人工修改、异常成本、错误自主和生产漂移接入回归。九十天不是“数字员工毕业”，只是形成持续提供授权证据的起点。

## 角色与职责

业务 owner 定义价值、损失和最终责任；领域专家提供案例和判定；FDE 连接流程、数据、环境和实验；Agent 工程师实现 Harness 与 Skill；平台团队保证工具可重置、可观察；风险团队定义 veto 与权限；Eval owner 独立维护协议、隐藏集、版本和申诉。

出题者可以和系统开发者合作，但资格集保管和最终门禁最好由独立角色负责。专家意见不一致时，记录分歧和升级路径，不要私下挑一个最容易自动评分的答案。

## 经济性不是“调用成本越低越好”

企业价值包括减少等待和返工、避免损失、增加吞吐与服务价值，再减去模型/工具成本、人工监督、环境维护、事故和机会成本。单位成功成本的分母应是“没有严重错误的完整闭环”，成本分子则要包含失败调用。否则，一个便宜但经常失败的系统会显得虚假高效。

还要看下游影响。Agent 可能减少自己环节的人工分钟，却让下游复核更多；平均处理时间变短，却让长尾客户等更久；自动关闭更多，却导致重开率上升。端到端周期、接管分钟、重开率和风险损失要一起看。

## 常见失败模式

- **从演示倒推构念**：先看模型会什么，再把容易成功的动作定义成岗位；
- **把 SOP 当真实分布**：只测理想路径，漏掉等待、例外和事故；
- **让同一位专家包办一切**：个人偏好被固化成答案，争议没有申诉；
- **用一个总分汇报**：日常成功掩盖罕见严重错误；
- **把升级当失败**：逼系统在证据不足时猜；
- **先给生产权限再补测试**：事故成了第一次真正的验收；
- **项目结束即冻结**：政策、工具和数据变了，资格证据还停在旧版本。

## 练习：选择第一条岗位切片

使用 `templates/fde_process_inventory.csv` 列出十条候选流程，按频率、可验证终态、错误损失、可逆性、数据可得和跨系统复杂度评分。选一个窄切片，并写出为何暂不自动化其他九条。
