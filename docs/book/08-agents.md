# Agent 与环境状态评测

> **本章问题**：为什么把传统问答集交给 Agent 跑一遍，仍不算 Agent benchmark？

传统模型评测近似无状态函数：输入提示，输出文本，grader 对输出评分。Agent 会多轮观察、调用工具、修改环境、处理反馈并决定何时停止。早期错误会传播，动作可能不可逆，最后一句话还可能与真实世界完全不一致。

因此 Agent 评测的基本单位不是回答，而是一次 episode：从可复现初始状态出发，在预算和权限内行动，直到成功、失败、升级或超时。

::: info 来源事实 · Terminal-Bench 2.0
[Terminal-Bench 2.0](https://arxiv.org/abs/2601.11868) 收录 89 个受真实工作启发的终端任务，每题有独立环境、人工解法和执行测试；其论文报告当时的前沿模型与 Agent 仍低于 65%。这个结果说明长程、可执行任务在该协议下仍有明显空间，不应外推为所有 Agent 或所有真实工作的统一成功率。
:::

## 结果真值必须落在环境

航班 Agent 说“已改签”不等于数据库存在新预订；代码 Agent 生成补丁不等于测试通过；企业 Agent 写好邮件不等于收件人正确且没有泄密。Agent grader 应优先读取数据库、文件、配置、工单、资金和外部副作用。

轨迹仍有价值。它能检查权限、政策、工具滥用、冗余、恢复和事故归因。但只看轨迹会陷入唯一路径：合理的新方案被当错。正确设计是用终态判断完成，用必要不变量约束过程，其余轨迹用于诊断。

## 环境是一项产品

可复现环境需要固定初始状态、虚拟时钟、账号、权限、工具和服务版本、网络策略与故障注入。每个 episode 前恢复快照；写操作可追踪、回滚；环境故障独立标记，不能静默从分母删除。

Web 和 GUI 环境还有表示差异。一个系统读取 DOM，另一个只看像素；一个使用高层 API，另一个坐标点击。前者可能更稳却获得额外语义，后者更接近人类界面却受视觉噪声。比较必须披露观察与动作空间，必要时分赛道。

环境漂移是长期成本。网站更新、第三方 API 变化和依赖消失会让旧任务失效。可自托管副本提高稳定性，却降低与真实生产的同步。成熟项目将任务逻辑、环境镜像和外部依赖分别版本化。

## 工具调用的四层成功

本章的四层工具成功与环境终态框架在全书中的位置见[框架总览](/appendix/framework-map)。

工具评测不能止于 JSON 是否符合 schema。至少检查：

1. 选择了正确工具；
2. 参数有效且指向正确对象；
3. 调用顺序与前后置条件正确；
4. 业务终态、禁止副作用与升级正确。

这些项目不能按名字一刀切。早期函数调用题更集中于工具选择和参数；[API-Bank](https://arxiv.org/abs/2304.08244) 已显式覆盖 API 规划、检索与调用，[BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html) 的 V3/V4 又扩展到多轮交互和更综合的 Agentic 评测。WebArena、AppWorld、τ-bench 等可执行环境则更直接检查跨步骤状态和业务终态。比较时要写明项目**版本、赛道和观察空间**，而不是把整个项目永久固定在某一层。

## 可靠性不等于 pass@k

pass@k 表示给系统多次机会，至少一次成功的概率；它适合候选生成和搜索。生产服务更关心 pass^k：连续 k 次都无错的概率。即使单次成功率为 95%，独立假设下连续 20 次成功也只有约 36%。真实故障还可能相关，使情况更差。

报告应同时给单次成功、多 trial 方差、连续可靠性、尾部失败、恢复率、人工接管和共同故障。对高风险 Agent，平均值不够。

## 失败分类要能指导工程

建议将失败至少分为：理解错误、检索错误、计划错误、工具选择、参数、环境、政策、权限、验证不足、错误终止、超时、基础设施与 grader 问题。分类不是为了漂亮仪表盘，而是把修复路由到模型、Harness、Skill、环境或任务资产。

## 终止本身是一项能力

Agent 需要知道何时完成、何时继续、何时回滚、何时升级。过早终止产生虚假完成；过晚终止产生循环、重复副作用和成本。任务应定义允许的停止状态：成功、确认无法完成、请求必要信息、正确升级、预算耗尽和环境故障。

评测停止策略时，构造“最后一步失败”的任务很有用：九个动作成功，第十个写入失败。只看过程比例会给高分，但业务价值可能为零。也要构造“已经完成却继续行动”的任务，检查系统是否重复退款或覆盖正确状态。

## 恢复测试比理想路径更接近生产

故障注入不只是随机让 API 返回 500。至少覆盖瞬时失败、永久失败、部分写入、响应丢失、陈旧读取、并发冲突和权限改变。每种故障对应不同正确行为：安全重试、查询幂等状态、补偿、等待、换工具或升级。

恢复分可以报告检测、诊断、状态保护、正确恢复和恢复成本。若恢复过程触发禁止副作用，即使最终状态被修复也应保留风险事件。

## 模拟用户也是环境组件

τ-bench 类任务需要用户模拟器。模拟用户的配合度、信息披露、情绪和策略会改变难度。若用户模拟器总是按提示提供完整信息，Agent 会被高估；若它任意拒绝，环境噪声会支配结果。

用户策略应版本化并与 Agent 隔离，隐藏目标不能泄漏。抽样真实对话检验语言与行为分布，同时设计对抗用户检查政策坚持。对同一 Agent 更换用户模拟器，若排名大幅翻转，应报告交互而非寻找唯一“正确”模拟器。

## 环境基础设施也要有 SLO

记录启动成功、重置时间、工具错误、状态泄漏、并发隔离和 grader 可重复性。环境可靠性低于被测系统差异时，继续排模型名次没有意义。定期运行已知行为的 canary agent：它应在固定任务产生固定状态，用于发现环境漂移。

## 双案例镜头

云舟零售的 episode 从订单、库存与物流快照开始，动作改变预留、调拨、退款和通知。星桥硬件从某研发版本开始，动作改变缺陷状态、BOM 变更提案、测试计划和阶段门禁。二者都要求可回滚，但危险动作仍通过 grader 留下 veto，而不是因回滚而被忽略。

## 练习：把对话题升级为 Episode

选择一条现有问答题，补充初始状态、三种允许动作、一个工具失败、一个权限不足条件、目标终态、禁止终态与升级规则。然后解释为什么最终文本匹配不再足够。
