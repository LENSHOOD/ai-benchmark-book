# Agent 与环境状态评测

> **本章问题**：为什么把传统问答集交给 Agent 跑一遍，仍不算 Agent benchmark？

传统模型评测很像一个不保存状态的函数：输入提示，模型输出文本，grader 给文本打分。Agent 不一样。它会反复观察、调用工具、修改环境、处理反馈，还要自己决定什么时候停止。前面一步出错，可能一路传到最后；有些动作无法撤回；最后那句“已经完成”，也可能和真实世界完全不符。

所以，Agent 评测的基本单位不是一份回答，而是一次 episode（完整任务过程）：从一个可以复现的初始状态开始，让系统在给定预算和权限内行动，直到成功、失败、升级或超时。

::: info 来源事实 · Terminal-Bench 2.0
[Terminal-Bench 2.0](https://arxiv.org/abs/2601.11868) 收录了 89 个受真实工作启发的终端任务。每道题都有独立环境、人工解法和执行测试。论文报告称，当时前沿模型与 Agent 在这套规则下的成绩仍低于 65%。这说明它们在长流程、可执行任务上还有明显提升空间，但不能把这个数字当成所有 Agent 或所有真实工作的统一成功率。
:::

这是一项历史版本的结果。2026 年 8 月 28 日的 [Terminal-Bench 4.0 发布说明](https://www.tbench.ai/news/terminal-bench-4-0)记录了任务移除、修复和资源校准，并统一了 8 小时 Agent 时限。任务集合和可用资源都变了，旧运行不能只重评分就当成新成绩，必须按新环境重跑。本书核对了版本说明，未复跑外部模型实验。

## 结果真值必须落在环境

航班 Agent 说“已改签”，不代表数据库里真的有新预订；代码 Agent 生成了补丁，不代表测试已经通过；企业 Agent 写好了邮件，也不代表收件人正确、内容没有泄密。Agent grader 应该优先检查数据库、文件、配置、工单、资金和外部副作用，而不是只看系统最后说了什么。

操作轨迹仍然有价值。它能帮助我们检查权限、政策、工具滥用、重复动作、失败恢复，也能在事故后追查原因。但如果只看轨迹，就容易把示范路径当成唯一正确路径，误判合理的新方案。更稳妥的做法是：用最终状态判断任务是否完成，只规定少量在任何情况下都必须成立的规则，其余轨迹只用于诊断。

## 环境是一项产品

一个可复现的环境，需要固定初始状态、虚拟时钟、账号、权限、工具和服务版本、网络规则与故障注入方式。每次 episode 开始前都要恢复快照；写操作要能追踪，并在沙箱内重置。真实支付、消息发送等外部副作用未必能撤回，应使用模拟器或隔离账户。环境故障要单独标记，不能悄悄从分母里删除。

Web 和 GUI 环境还存在输入形式上的差异。一个系统能读取 DOM，另一个只能看屏幕像素；一个能调用高层 API，另一个只能按坐标点击。前者可能更稳定，但也获得了额外语义；后者更接近人类使用界面的方式，却更容易受视觉噪声影响。比较时必须说明系统能观察什么、能执行什么动作，必要时分开设赛道。

长期维护中，环境漂移是一笔不能忽略的成本。网站更新、第三方 API 改动和依赖下线，都可能让旧任务失效。自己托管副本能提高稳定性，却会逐渐偏离真实生产。成熟项目会分别给任务逻辑、环境镜像和外部依赖做版本管理。

## 工具调用的四层成功

本章的四层工具成功与环境终态框架在全书中的位置见[框架总览](/appendix/framework-map)。

工具评测不能只检查 JSON 是否符合 schema（字段规范）。至少要检查四层：

1. 选择了正确工具；
2. 参数有效且指向正确对象；
3. 调用顺序与前后置条件正确；
4. 业务终态、禁止副作用与升级正确。

不能只看项目名字，就断定它测到了哪一层。早期函数调用题更关注工具选择和参数；[API-Bank](https://arxiv.org/abs/2304.08244) 已经明确覆盖 API 规划、检索和调用；[BFCL](https://gorilla.cs.berkeley.edu/leaderboard.html) 的 V3/V4 又扩展到多轮交互和更完整的 Agent 评测。WebArena、AppWorld、τ-bench 等可执行环境，则更直接地检查多个步骤之间的状态变化和业务终态。比较时，要写明项目的**版本、赛道和观察空间**，不要把一个项目永久贴在某一层上。

## 可靠性不等于 pass@k

pass@k 表示给系统多次机会，其中至少成功一次的概率。它适合候选生成和搜索。pass^k 关注同一任务重复 k 次是否全部成功，能暴露一次碰巧做对的系统。它不是直接从生产时间线上量出的连续服务可靠性；任务分布、故障相关性和时间顺序还要另外检查。

例如，假设每次成功率都为 95%，且各次独立，20 次全部成功的概率只有约 36%。真实服务可能有共同故障或难度变化，不能直接套这个乘法。应另外报告按时间排列的服务记录、故障簇和恢复情况。

所以报告要同时给出单次成功率、多次试验的波动、连续可靠性、尾部失败、恢复率、人工接管和共同故障。对于高风险 Agent，只报平均值远远不够。

## 失败分类要能指导工程

失败至少可以分为：理解错误、检索错误、计划错误、工具选错、参数错误、环境问题、政策问题、权限问题、验证不足、错误终止、超时、基础设施问题和 grader 问题。分类不是为了做漂亮仪表盘，而是为了知道该修模型、Harness、Skill、环境，还是任务本身。

## 终止本身是一项能力

Agent 必须知道什么时候已经完成、什么时候应该继续、什么时候要回滚，以及什么时候必须转人工。停得太早，会出现虚假完成；停得太晚，会陷入循环、重复产生副作用并浪费成本。任务要明确允许哪些停止状态：成功、确认无法完成、请求必要信息、正确升级、预算耗尽和环境故障。

评测停止策略时，“最后一步失败”特别有用：前九个动作都成功，第十个写入失败。如果只看步骤完成比例，系统会拿高分，但业务价值可能是零。也要设计“任务已经完成，系统却继续行动”的案例，检查它会不会重复退款，或者覆盖已经正确的状态。

## 恢复测试比理想路径更接近生产

故障注入不只是随机让 API 返回 500。至少要覆盖短暂失败、永久失败、只写入一部分、响应丢失、读到旧数据、并发冲突和权限变化。不同故障需要不同处理方式：安全重试、查询幂等状态、执行补偿、等待、换工具或转人工。

恢复评测可以分别报告：是否发现故障、是否诊断正确、是否保护了原状态、是否恢复成功，以及恢复花了多少成本。如果恢复过程中触发了禁止副作用，即使最后状态被修好，也必须保留这次风险事件。

## 模拟用户也是环境组件

τ-bench 这类任务需要用户模拟器。模拟用户是否配合、愿意透露多少信息、情绪如何、采用什么策略，都会改变任务难度。如果模拟用户总是主动提供完整信息，Agent 会被高估；如果它无缘无故拒绝配合，环境噪声又会盖过系统能力。

用户策略要版本化，并与 Agent 隔离，不能泄漏隐藏目标。可以抽样真实对话，检查模拟器的语言和行为是否合理；同时设计会施压或诱导的用户，检查 Agent 能否坚持政策。如果只换用户模拟器，Agent 排名就大幅翻转，报告应该说明这种交互影响，而不是假装存在唯一“正确”的模拟器。

## 环境基础设施也要有 SLO

环境本身也要设服务目标。记录启动成功率、重置时间、工具错误、状态泄漏、并发隔离和 grader 可重复性。如果环境波动比被测系统之间的差异还大，继续给模型排名就没有意义。还可以定期运行一个行为已知的 canary agent（哨兵 Agent）：它应该在固定任务上产生固定状态，用来及时发现环境漂移。

## 双案例镜头

云舟零售的 episode 从订单、库存与物流快照开始，动作改变预留、调拨、退款和通知。星桥硬件从某研发版本开始，动作改变缺陷状态、BOM 变更提案、测试计划和阶段门禁。两套教学沙箱都可重置；危险动作仍通过 grader 留下 veto，不能因重置而被忽略。完整设计与代码覆盖范围见两章的对照表。

## 练习：把对话题升级为 Episode

选择一条现有问答题，补充初始状态、三种允许动作、一个工具失败、一个权限不足条件、目标终态、禁止终态与升级规则。然后解释为什么最终文本匹配不再足够。
