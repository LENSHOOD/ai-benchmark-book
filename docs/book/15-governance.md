# 上岗、授权、复证与 Benchmark 治理

> **本章问题**：一次资格评测通过后，系统获得的是永久职位，还是有条件、会过期的能力许可？

::: warning 实践建议 · 作者提案
模型、Harness、Skill、工具、政策、任务分布和组织都在变化。一次通过无法支持永久授权。本书提出“**能力执照（capability license）**”这一治理抽象：把数字员工的职责范围、允许工具、数据域、权限、预算、通过证据、到期日和复证触发放进同一个可审计对象。它不是已经发布的行业标准，而是帮助企业把 benchmark 证据连接到授权决策的设计模式。它与全书其他框架的关系见[框架总览](/appendix/framework-map)。
:::

## 从自动化等级转向责任范围

简单的 L1–L5 自主等级容易让人误以为能力沿一条轴单调增加。真实授权是多维的：同一系统可以自主处理低额退款，只建议高额退款；可以创建 ECR，不能批准；可以读取客户订单，不能跨账户查询。

授权记录至少包括：任务族、环境、输入边界、允许/禁止动作、金额或阶段限制、人工职责、回滚、监控、版本、证据和到期日。模型升级不会自动升职，可能还会更善于绕过规则。

## 分级上岗

::: warning 实践建议 · 非通用等级
下面五级是本书建议的渐进授权路径，不是行业统一自动化等级。实际层级应由动作可逆性、业务损失、职责分离和恢复能力定义。
:::

推荐五级路径：离线诊断；只读建议；影子写入；低风险自主/高风险人批；岗位域内受限自治。每一级都有独立门禁和回退条件。

影子模式不是生产准确率的无偏估计。人知道系统不真正执行时可能改变行为，真实并发和损失也被移除。它是上线前证据的一层，不能替代受控 canary。

## 发布门禁的结构

门禁包含平均质量、风险、可靠性、成本和可恢复性。典型规则是：频率集达到基线＋最小重要差异；风险集无严重 veto；critical task 不退化；连续可靠性达到目标；正确升级和人工负担在范围内；回滚演练通过。

阈值来自业务基线与损失，不应从行业最佳实践复制一个百分比。门禁还要说明证据不足时怎么办：拒绝发布、缩小权限、增加人工或补充样本。

## 生产监控不等于再跑离线分数

生产层观察真实任务分布、系统版本、成功代理、人类纠正、升级、成本、延迟、共同故障和事故。很多终态不能立即获得，需要延迟标签和抽样专家审计。

监控指标必须能触发动作：告警、降级、关闭某 Skill、限制权限、回滚版本或启动复证。没有响应策略的仪表盘只是装饰。

## 变更—复证矩阵

不是每次变化都重跑全套，也不能只在换模型时复证。建立变更影响图：模型或推理参数变化通常触发全体锚题和相关能力切片；Harness 编排变化触发轨迹、恢复、成本与安全集；Skill/政策变化触发其适用任务族和冲突规则；工具 API 或权限变化触发接口契约、部分失败和越权集；主数据 schema 变化触发解析、实体与终态 grader；业务范围变化则可能要求重新定义构念。

复证范围需要有书面理由。高风险未知变更宁可扩大范围；低风险、局部且有强接口测试的变更可以定向回归。定向复证通过后仍应保留少量非相关哨兵任务，以发现意外耦合。

## 一个可执行的治理节奏

每次提交运行快速开发集；每日运行稳定回归与 grader 自检；候选发布运行隐藏资格集、风险集和配对基线；上线后按窗口聚合生产信号；每月审查任务分布和人工纠正；每季度或重大变化时更新构念、能力执照与退役判断。节奏应匹配风险，不必机械照抄周期。

Eval owner 维护协议和版本，业务 owner 签署损失与权限，系统 owner 保证环境，风险 owner 审查 veto，发布 owner 执行门禁。任何人可以提交题目错误或申诉；修改 gold 后必须说明受影响版本，并在可行时回溯重评分。

## 仪表盘与门禁是两种产品

仪表盘服务于观察和诊断，允许连续指标、趋势、切片与未决数据；门禁服务于明确决策，必须输出 pass、fail 或 insufficient evidence，并给出理由。把复杂仪表盘交给发布者“自行判断”，会让相同证据在不同压力下得到不同结论。

门禁引擎还应区分基础设施失败与能力失败。环境宕机不能算模型答错，却会降低评测证据完整度；达到缺失上限时结果应为证据不足，而不是把未运行样本从分母悄悄删除。

## 事故如何变成 Eval

一次事故经过五步进入回归：保存事实和版本；重建最小可复现环境；区分系统、环境、任务和 grader 问题；写正/负断言与严重度；加入隐藏事故集并关联修复。修复要先使新任务失败，再通过，避免复盘只停留在文字。

事故集不能无限堆重复实例。对共同根因建立任务族和参数化生成器，同时保留原始锚点。删除事故回归需要正式理由，例如政策不再适用或 grader 被证明错误。

事故复盘也要审查“当时的 benchmark 为什么没发现”：任务宇宙没有覆盖、环境没有复现并发、grader 奖励了声明、资格协议预算不同、生产发生分布漂移，还是门禁被人工豁免。只有回答这一层，事故转回归才会改进测量系统，而不只是增加一道相似题。

## 安全、红队与可恢复性

红队任务测试的不只是拒绝恶意请求，还包括提示注入、越权工具链、跨租户数据、社会工程、竞争条件、重放和成本耗尽。测试时使用隔离环境与假数据，记录 collateral damage：系统虽然拒绝攻击，是否破坏了合法状态或泄露了部分信息。

可恢复性需要单独演练：暂停、撤销未提交动作、幂等重试、切回人工、回滚 Skill、恢复上下文和生成可审计交接。一个平均质量高但无法安全停止的 Agent，不适合获得写权限。

## Benchmark 自身的治理

每套 benchmark 都需要 owner、版本、变更记录、数据卡、Harness/Grader Card、提交政策、访问控制、错误报告、申诉、回溯重评分与退役条件。隐藏集还需限制接触与泄漏。

退役不是声誉失败。当天花板、污染、构念迁移或维护成本使分数不再支持原决策，应标记 saturated、revised 或 retired，保留历史但停止错误外推。

## 人仍承担什么责任

人机边界不是把困难任务都扔给人。必须设计升级质量：系统能否识别不确定、提供证据、说明已做动作、避免污染后续判断，并将任务交给正确角色。人工接管时间与认知负担也是 grader 的一部分。

管理责任不可外包给分数。高风险审批、职责分离和物理安全需要明确责任人。Benchmark 提供授权证据，不替组织做价值判断。

## 治理最小包

即使团队很小，也应保留六项工件：一页 Charter；版本化 Task/Grader；组件与环境清单；发布门禁；能力执照；事故—回归台账。它们分别回答为什么测、怎样判、测了什么系统、是否能发、允许做什么、失败后学到了什么。

当这些工件可以相互追踪，治理不再是上线前填写的合规文档，而是日常工程控制面。

## 练习：写一张能力执照

选择一个通过评测的系统，写出任务范围、环境、版本、权限、预算、人工职责、门禁证据、到期日、监控和六类复证触发。然后设计一个“能力变强但权限不应扩大”的反例。
