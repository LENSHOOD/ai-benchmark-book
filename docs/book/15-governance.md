# 数字员工怎样上岗，又怎样被收回权限

> **本章问题**：一次资格评测通过后，系统获得的是永久职位，还是有条件、会过期的能力许可？

答案应该是后者。数字员工拿到的不是“永久编制”，而是一组有限权限：只能做哪些任务、在什么条件下做、做到什么时候、出了什么变化要重新考试。

::: warning 实践建议 · 作者提案
模型、Harness、Skill、工具、政策和业务都在变，一次通过不能支持永久授权。本书用“**能力执照（capability license）**”管理这件事：把职责范围、允许工具、数据范围、权限、预算、通过证据、到期日和重考条件写在同一张可审计记录里。它不是行业标准，而是本书给企业的治理模板。它与全书其他框架的关系见[框架总览](/appendix/framework-map)。
:::

## 从自动化等级转向责任范围

简单的 L1–L5 容易让人误以为系统只会“越来越自主”。真实权限不是一条直线。同一系统可以自己处理低额退款，却只能建议高额退款；可以创建 ECR，不能批准；可以看本客户订单，不能跨账户查询。

授权记录至少包括：任务族、环境、输入边界、允许/禁止动作、金额或阶段限制、人工职责、回滚、监控、版本、证据和到期日。模型升级不会自动升职，可能还会更善于绕过规则。

## 分级上岗

::: warning 实践建议 · 非通用等级
下面五级是本书建议的渐进授权路径，不是行业统一自动化等级。实际层级应由动作可逆性、业务损失、职责分离和恢复能力定义。
:::

推荐按五步放权：离线诊断；只读建议；影子写入；低风险自主、高风险人批；岗位范围内的受限自治。每一级都有自己的通过条件和退回条件。

影子模式也不等于真实生产。人知道系统不会真的执行，行为可能改变；真实并发和损失也没有发生。它只是上线前的一层证据，不能替代小流量 canary。

## 发布门禁的结构

发布门禁至少看五件事：日常质量、严重风险、多次运行是否稳定、成本是否可接受、出错后能否恢复。常见规则是：日常题达到基线加预先约定的最小重要差异；风险题没有严重 veto；关键任务不退步；连续运行够稳定；正确求助和人工负担都在范围内；回滚演练通过。

阈值来自业务基线与损失，不应从行业最佳实践复制一个百分比。门禁还要说明证据不足时怎么办：拒绝发布、缩小权限、增加人工或补充样本。

## 生产监控不等于再跑离线分数

生产层观察真实任务分布、系统版本、成功代理、人类纠正、升级、成本、延迟、共同故障和事故。很多终态不能立即获得，需要延迟标签和抽样专家审计。

监控指标必须能触发动作：告警、降级、关闭某 Skill、限制权限、回滚版本或启动复证。没有响应策略的仪表盘只是装饰。

## 变更—复证矩阵

不是每次变化都要重跑全套，也不能只在换模型时重考。先画变更影响图：换模型或推理参数，跑全部锚题和相关能力切片；改 Harness，重点跑轨迹、恢复、成本和安全题；改 Skill 或政策，跑对应任务族和冲突题；改工具 API 或权限，跑接口、部分失败和越权题；改主数据格式，跑解析和终态评分；业务范围变了，可能连“到底测什么”都要重写。

复证范围需要有书面理由。高风险未知变更宁可扩大范围；低风险、局部且有强接口测试的变更可以定向回归。定向复证通过后仍应保留少量非相关哨兵任务，以发现意外耦合。

## 一个可执行的治理节奏

一个可执行节奏是：每次提交跑快速开发集；每天跑稳定回归和评分器自检；候选发布前跑隐藏资格集、风险集和配对基线；上线后汇总生产信号；每月看任务分布和人工纠正；每季度或发生重大变化时更新能力定义、执照和退役判断。周期可以按风险调整。

Eval owner 维护协议和版本，业务 owner 签署损失与权限，系统 owner 保证环境，风险 owner 审查 veto，发布 owner 执行门禁。任何人可以提交题目错误或申诉；修改 gold 后必须说明受影响版本，并在可行时回溯重评分。

## 仪表盘与门禁是两种产品

仪表盘用来观察和找原因，可以展示趋势、切片和未完成数据。门禁用来做决定，只能给出通过、失败或证据不足，并说明原因。把一张复杂仪表盘扔给发布者“自己判断”，同样的数据会在不同压力下得到不同答案。

门禁引擎还应区分基础设施失败与能力失败。环境宕机不能算模型答错，却会降低评测证据完整度；达到缺失上限时结果应为证据不足，而不是把未运行样本从分母悄悄删除。

## 事故如何变成 Eval

事故变成回归题要走五步：保存当时事实和版本；重建最小环境；分清是系统、环境、题目还是评分器的问题；写清正确和错误条件以及严重度；放进隐藏事故集并关联修复。先确认旧系统会在新题上失败，再确认修复后通过。

事故集不能无限堆重复实例。对共同根因建立任务族和参数化生成器，同时保留原始锚点。删除事故回归需要正式理由，例如政策不再适用或 grader 被证明错误。

事故复盘也要审查“当时的 benchmark 为什么没发现”：任务宇宙没有覆盖、环境没有复现并发、grader 奖励了声明、资格协议预算不同、生产发生分布漂移，还是门禁被人工豁免。只有回答这一层，事故转回归才会改进测量系统，而不只是增加一道相似题。

## 安全、红队与可恢复性

红队不只测系统会不会拒绝恶意请求。还要测提示注入、越权工具、跨租户数据、社会工程、并发竞争、重放和成本耗尽。用隔离环境和假数据，并记录附带伤害：系统虽然拒绝了攻击，有没有顺手破坏合法状态或泄露一部分信息。

可恢复性需要单独演练：暂停、撤销未提交动作、幂等重试、切回人工、回滚 Skill、恢复上下文和生成可审计交接。一个平均质量高但无法安全停止的 Agent，不适合获得写权限。

## Benchmark 自身的治理

每套 benchmark 都要有人负责，并有版本、变更记录、数据卡、Harness/Grader Card、提交规则、访问控制、报错、申诉、重新评分和退役条件。隐藏集还要限制谁能接触。

退役不是声誉失败。当天花板、污染、构念迁移或维护成本使分数不再支持原决策，应标记 saturated、revised 或 retired，保留历史但停止错误外推。

## 人仍承担什么责任

人机分工不能变成“难题都扔给人”。系统求助时要带上证据、已经做过的动作和不确定点，并把任务交给正确角色。人工接管要花多久、要重新读多少材料，也应进入评分。

管理责任不可外包给分数。高风险审批、职责分离和物理安全需要明确责任人。Benchmark 提供授权证据，不替组织做价值判断。

## 治理最小包

即使团队很小，也应保留六项工件：一页 Charter；版本化 Task/Grader；组件与环境清单；发布门禁；能力执照；事故—回归台账。它们分别回答为什么测、怎样判、测了什么系统、是否能发、允许做什么、失败后学到了什么。

当这些材料能互相追到，治理就不再是上线前填一张合规表，而是每天真的在用的工程规则。

## 练习：写一张能力执照

选择一个通过评测的系统，写出任务范围、环境、版本、权限、预算、人工职责、门禁证据、到期日、监控和六类复证触发。然后设计一个“能力变强但权限不应扩大”的反例。
