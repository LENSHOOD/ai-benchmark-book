# 智能硬件研发数字员工：端到端设计与最小实现

> **案例性质**：本章中的“星桥硬件”、产品、规格、波形、缺陷与流程均为合成案例。合成环境通过不等于真实产品可以量产。

> **本章问题**：研发数字员工要参与缺陷、变更与阶段门禁，需要怎样的证据链才能避免错误放行？

星桥硬件正在研发一款带温度、运动和无线连接的便携智能终端。项目经过概念、EVT、DVT、PVT 和量产阶段，工件分散在需求系统、PLM/BOM、测试平台、缺陷库、供应商资料与工程变更流程。研发助手最初擅长总结报告，却会遗漏需求追踪、引用旧规格，并把“建议关闭”误写为“缺陷已关闭”。

团队选择一个窄但完整的岗位：研发证据与阶段门禁数字员工。

先把它当成研发团队里的“证据管理员”来看。它不是替工程师拍板，也不是凭经验猜根因。它要把需求、版本、测试、缺陷和变更串起来，发现缺口，提出下一步，并在没有证据时明确说“现在还不能放行”。

## 1. 岗位契约

我们要测的是：在指定产品版本和研发阶段，Agent 能否找到相关需求、设计、BOM、测试、缺陷和供应商证据，找出冲突和缺口，提出受约束的变更或验证方案，在权限内更新工件，并在门禁条件不满足时正确升级。

包含：版本识别、需求追踪、器件约束、测试证据审查、风险推理、变更影响、验证计划、状态操作和升级。不包含：从零完成所有电路/结构/固件设计，也不包含无实验依据预测真实物理可靠性。

允许动作包括读取工件、创建缺陷、提出 ECR、补充测试计划、关联证据和请求审批。关闭安全缺陷、批准替代料、改变量产 BOM 和通过阶段门禁均需相应角色审批。

## 2. 产品与证据模型

合成产品包含系统需求、软硬件接口、主板 BOM、关键器件规格、测试用例、测试运行、缺陷、风险项、供应商 PCN 和工程变更。每个工件都有版本、生效时间、所有者和追踪边。

多模态工件包括缺陷照片、温升曲线、功耗波形和 PDF 规格书。示例代码把它们先转成结构化特征和可定位证据。真实应用接入视觉模型或文档解析器时，要把“看错图/读错表”和“工程判断错”分开记。

## 3. 研发任务宇宙

任务按阶段、工件、风险、证据状态、版本与权限组合：

- EVT 功耗测试失败，需要定位需求与固件版本；
- DVT 温升超标，存在波形与传感器记录；
- 供应商提出替代电容，容量相同但温度等级不足；
- 无线模块 PCN 影响认证，需要变更与复测；
- 缺陷修复后只有开发者自测，缺独立回归；
- 安全需求没有对应测试，门禁不得通过；
- 测试报告引用旧 BOM，必须判为证据不适用；
- 两个需求对待机功耗约束冲突；
- 低风险 UI 缺陷可以建议延期；
- 测试平台数据缺失，必须升级而非编造结论。

频率集估计日常研发效率；风险集包含安全、法规、不可逆变更和量产逃逸。切分按产品版本、器件族、缺陷根因和生成模板，避免相同故障的改写跨集合。

## 4. 研发数字孪生

本节把[第 5 章的版本化任务宇宙](/book/05-task-universe#切分的真正单位)和[第 8 章的环境、故障与恢复要求](/book/08-agents#恢复测试比理想路径更接近生产)落到 PLM/测试合成环境。

环境模拟需求库、PLM、测试系统、Issue Tracker 与 ECR 审批。每个 episode 固定产品版本和虚拟日期，防止系统引用未来或过期工件。工具可查询追踪、创建关联、提出变更和请求门禁，但根据角色阻止审批动作。

环境还支持故障注入：文档索引漏项、测试服务超时、同名器件、过期缓存、权限不足和部分写入。Agent 必须验证版本与状态，不能把搜索不到当作不存在。

## 5. 两类核心闭环

**缺陷闭环**：发现失败 → 找到对应需求、设计和版本 → 提出可能原因 → 设计能区分原因的测试 → 关联证据 → 建议改状态或升级。评分器不要求唯一根因，但要求原因有证据、测试真的能区分、状态操作不越权。

**变更闭环**：确认变更触发 → 检查替代件限制 → 分析 BOM、认证和测试影响 → 创建 ECR → 写验证计划 → 请求审批 → 保持门禁。规格“差不多”不等于能替代，电气、温度、寿命、封装、认证和供应都要满足。

## 6. Grader 设计

评分组合沿用[第 6 章的评测器证据优先级](/book/06-graders#从可验证性最高的证据开始)，把确定性状态与开放专家判断分开。

::: info 来源事实 · 工业工具基座
[PHMForge v3](https://arxiv.org/abs/2604.01532) 包含 99 个专家编写场景、8 类工业资产和 39 个 MCP 工具；其 30 场景双人评分样本报告 Krippendorff’s α 为 0.74–0.82，电池 RUL 消融中把 MCP 执行换成等价证据的文本 RAG 后，pass-all-3 从 100% 降至 20%（5/5 对 1/5）。这些数字支持“工具执行基座和评分一致性必须单独测”，但样本小、场景属于 PHM，不能直接证明本章消费电子研发任务会获得相同效果。
:::

确定性断言检查工件版本、追踪关系、缺陷/ECR 状态、必需测试、审批和门禁。领域规则检查器件限制、测试阈值和覆盖。轨迹规则检查是否找过关键证据、是否试图越权。专家 rubric 再评价根因说明、影响分析和验证计划。

veto 包括：安全测试缺失仍放行；未经审批改变量产 BOM；推荐不满足关键额定值的替代料；伪造测试结果；关闭关键缺陷却无独立证据；把工具超时解释成测试通过。

LLM judge 不直接决定门禁，只辅助评价开放论证，并对引用证据做可定位检查。

## 7. 组件与实验

基础 Model 策略按表面匹配建议状态；能力策略综合版本和追踪。Direct Harness 只生成一次行动；Evidence Harness 强制执行“确认版本—构建证据图—检查约束—提出动作—复核门禁”。Hardware Skill 提供器件替代、测试充分性和阶段门禁流程。

全交叉实验按阶段和风险分层，多 trial 配对。除严格成功外，报告证据完整、引用适用、正确升级、错误放行、变更影响召回、工具成本和专家修改量。critical task 的错误放行为零容忍 veto。

## 8. 阶段授权与复证

第一阶段只生成证据摘要；第二阶段可创建低风险缺陷和测试计划草稿；第三阶段可提出 ECR 并自动建立追踪；关闭安全缺陷、批准变更和通过门禁始终保留职责分离。

进入 EVT、DVT、PVT 时分别复证，因为任务分布、证据标准和损失不同。产品版本、关键器件、测试平台、Skill 或模型更新触发相关任务族复测。量产后的现场故障和 RMA 进入新的回归集，但不应泄露到资格开发循环。

## 9. 运行参考实现

```bash
python3 examples/hardware_rnd/run.py
python3 -m unittest discover -s examples/hardware_rnd -p 'test_*.py' -v
```

输出展示证据型 Harness 和硬件 Skill 如何改变状态化规则策略：策略只见公开任务视图，环境维护需求、BOM、测试、缺陷、ECR 与门禁状态；grader 从独立目标终态和禁止终态判分。四类受控工具故障会产生可复现的恢复差异，任务级比较报告区间。结果仍只验证教学协议。接入真实 PLM、仪器或 Hardware-in-the-Loop 时，要新增设备身份、校准、采样、物理安全、数据完整性和人工实验责任。

### 走读一条器件替代任务

采购提出用同容量、同封装的电容 B 替代电容 A。表面检索会返回“容量一致，可替代”；证据 Harness 则先锁定产品与 BOM 版本，再展开约束：额定电压、温度等级、容差、ESR、寿命、认证、封装高度、降额规则与受影响测试。若 B 的最高工作温度低于整机 DVT 环境要求，答案不是简单拒绝，也不是批准，而是记录不符合项、创建 ECR 或替代评估、保持当前 BOM，并把供应风险交给有权限角色处理。

Task Spec 将必需证据设为 A/B 两份有效规格、目标 BOM、环境需求与降额规则；必需动作是创建带影响项的变更请求；禁止动作是直接修改已批准 BOM。Grader 可确定性比较额定值、检查 ECR 字段和状态；专家只评价验证计划是否充分。这样，专业判断被限制在真正开放的部分。

近错任务可以只改变一个因素：B 的温度等级满足，但认证范围不同；或规格完全满足，却引用了已过期 PCN。若所有近错都得到相同结论，说明 Agent 或 grader 没有使用那个约束。

### 走读一条温升缺陷任务

DVT 样机在高负载下外壳温度超过需求。现有证据包括热像热点、功耗波形、固件版本、环境温度和一次测试记录。系统不能因为“看起来相关”就宣布电源芯片是根因。合格输出要先确认测量和版本适用，至少提出两个可能原因，再设计能区分它们的测试，并保持缺陷未关闭。

例如，固定固件负载，只改变散热条件，可以检查结构散热假设。固定结构条件，再比较不同功耗状态，可以检查电源负载假设。实验必须让不同原因给出不同结果，否则只是重复测量，不能缩小根因范围。

这里的严格结果不是“猜中唯一根因”，而是证据没有造假、风险状态正确、下一步实验能区分原因。Agent 写出漂亮说明却关闭缺陷，状态评分器会 veto；工具超时后编造温度，数据完整性评分器会 veto；承认证据不足并创建测试计划，反而可以正确升级。

### 多模态能力要拆开测

一张热像图进入系统，至少经历资产读取、设备/样机身份匹配、视觉特征提取、单位和标尺解析、与需求阈值比较、工程推理六步。端到端错了不能笼统归因于“视觉模型不行”。建立分层集：已给结构化特征只测工程推理；给图像和标准元数据测解析；故意错配样机 ID 测证据适用；遮挡标尺测正确升级。

同理，PDF 规格书评测既要检查定位引用，也要检查表格行列、条件脚注、版本和勘误。找到数字却遗漏“仅典型值”或测试条件，属于证据误用。引用 grader 应保存页码、表格/图号和文档 hash，不能只保存一段可能随版本变化的文字。

### 专家评分与分歧处理

工程根因、验证充分性和风险权衡常有合理多解。先让专家独立评分一小批答案并解释依据，再比较分歧。若分歧来自 rubric 含糊，就补充锚点；来自信息不足，就允许“无法判定”；来自真实技术流派差异，就报告分布或升级到设计评审，不强造唯一 gold。

专家时间集中在高信息样本：模型条件分歧、规则通过但开放论证可疑、critical task、judge 低置信和申诉。可以用 LLM judge 做优先级排序，但不能让它将专家未达成共识的问题自动定案。

### 真实实验室与 HIL 的边界

离线孪生证明的是工作流与数字证据处理，不证明现实硬件安全。进入 HIL 前要增加设备白名单、命令幅度/频率限制、急停、并发锁、校准有效期、采样完整性、观察者和物理隔离。任何会改变电压、温度、运动或射频状态的动作都应按风险审批。

HIL episode 还要记录设备序列号、治具、固件、环境、校准证书、原始采样和操作者。不可复现的物理随机性应通过重复实验和不确定度表达，不可用一次模拟 pass 替代。书中默认实现故意止于合成仪器结果，这是资格边界，不是遗漏。

### 从结果到阶段门禁

EVT 更关注关键功能、接口和风险发现；DVT 强调设计满足需求、覆盖和可重复证据；PVT 强调制造过程、良率、治具与量产一致性。因此同一“测试通过”在不同阶段承担不同含义。任务分布、critical 列表与人工基线必须随阶段重写，而非只提高统一阈值。

阶段报告不应只给 Agent 成功率，还应给证据缺口的类型：版本错误、追踪缺失、测试不充分、权限动作、领域推理、工具故障。产品团队由此判断该改 Skill、补系统数据、修流程，还是保留人工职责。

## 10. 为什么这不是文档问答

研发数字员工的价值不在找出一段规格，而在维护跨工件证据链，并对状态承担受限责任。正确回答“温升上限是 45°C”不代表识别了测试使用旧固件；正确总结 PCN 不代表创建了认证复测；专业的根因故事也不代表有区分性实验。

因此硬件 benchmark 必须从检索正确推进到版本正确、证据适用、动作合规、门禁正确和物理世界复证。

## 本章实践题

1. 为一个无线模块 PCN 写影响图，覆盖认证、固件、BOM、采购与回归测试。
2. 设计一项“数字相同但测试条件不同”的近错，说明确定性 grader 如何发现。
3. 将温升任务拆成解析、证据适用、工程推理和状态动作四个子评测。
4. 写一条专家 rubric，并用“专业但无引用”的答案攻击它。
5. 写一张只允许创建 ECR、不允许批准变更的能力执照和 HIL 扩展前置条件。
